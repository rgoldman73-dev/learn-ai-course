## 🌿 The ecology hook

Every field biologist learns the same lesson the hard way: you will not remember it. The notebook records the date, the site, the weather, the odd behaviour you were sure you'd never forget. The herbarium sheet keeps a voucher specimen, with its label, long after the collector has retired. External memory is what lets an expedition's knowledge outlive the expedition, and lets someone else check it decades later.

Agents need the same thing, for the same reason. Their working memory, the context window, is limited, and it's wiped between sessions. Today you'll separate the three kinds of agent memory, and build the field notebook your capstone will use: plain Markdown notes, an index file the agent reads first, and two commands, one to file new notes and one to answer questions from them, with citations. Then you'll test its recall the way you'd test an observer: with questions you already know the answers to.

## 📖 Concept: working memory, compaction and the notebook

### Three layers of memory

```text
 ┌───────────────────────────────┐
 │ WORKING CONTEXT (window)      │  everything the model can attend to right now;
 │ instructions · recent turns   │  wiped when the session ends
 └──────────────┬────────────────┘
                │ fills up
 ┌──────────────▼────────────────┐
 │ COMPACTION                    │  older turns replaced by a summary;
 │ summary of the middle         │  lossy, and lossier each time it repeats
 └──────────────┬────────────────┘
                │ read / write by tool calls
 ┌──────────────▼────────────────┐
 │ EXTERNAL MEMORY (files, DB)   │  notebook, decisions log, MEMORY.md;
 │ survives sessions             │  found again by an index or by search (m20–m21)
 └───────────────────────────────┘
```

**Working context.** The Claude Code guide calls the context window the concept that explains everything: your messages, every file read and every command's output go in, and when it fills, the model performs worse and starts forgetting early instructions. Hence `/clear` between tasks and “one task, one conversation” [S:2104402058963026288].

**Compaction.** CMU's long-context lecture describes how agents compress history [S:2104635196910030894]. A trigger (a token threshold, the provider's hard limit, or a manual request) fires; the system protects the beginning, keeps the recent tail, and replaces the middle with a summary, sometimes a structured one with required fields. The risks are real: repeated compaction loses more each time, and the lecturer describes a compaction method their research group tuned that cost nothing on a coding benchmark, yet in real use made the agent open the same pull request five times and forget instructions the user had given mid-conversation. The lesson: benchmark scores can hide memory failures, so test in realistic conditions. The lecture also notes that coding agents usually keep the full history on disk, so you can tell the agent to go back and re-read it [S:2104635196910030894].

**External memory.** CMU's memory lecture traces this back to MemGPT, which borrowed the idea of a memory hierarchy from operating systems: a fast, small working context inside the window, and a large, slower external store, with reads and writes controlled by the model's own tool calls [S:2104635196910030894]. Later systems such as Mem0 also **update and delete**: they extract candidate facts from each new message, retrieve similar stored facts, and decide whether to add, replace or remove (“I work at X” followed weeks later by “I got laid off”) [S:2104635196910030894].

The harness-design article in the pack boils the practical rule down to one line: if it isn't in a file, it doesn't exist. It also recommends **pinning** the rules that must never be summarised away (safety limits, fixed contracts) in a file the agent re-reads after every reset [S:2106479644354474463].

### The second brain: Markdown plus a map

Three articles in the pack describe almost the same design for a personal knowledge base an agent can use.

- **Flat files and a map.** Bober's guide: plain `.md` files in a few semantic folders (`notes/`, `people/`, `projects/`), root files such as `MEMORY.md`, `LEARNINGS.md` and `decisions.md`, and a `CLAUDE.md` index that tells the agent where things live and how to read them. **One topic per file**, named for its content (`tax-policy.md`, not `note-12.md`), lower case with hyphens. Pull core files into every session with `@` imports, but sparingly [S:2078784709253841039]. That's the m05 idea, “a map, not a manual”, applied to your own knowledge.
- **An operating manual and commands.** CyrilXBT's course adds rules to `CLAUDE.md` (one idea per note, a one-line bold summary, a Links section) and safety rules: never delete, only archive; show a plan before moving more than 20 files; cite every note used; and “if my notes do not contain the answer, say so” [S:2106195341485703442]. Then it saves prompts as commands: `/process` empties the inbox into clean notes and links them; `/ask` answers **only from your notes**, lists the supporting line from each note, says where your notes disagree, and says what they *don't* cover [S:2106195341485703442]. Its `/draft` command marks anything not found in your notes as `[ADDED]` so you can check it [S:2106195341485703442].
- **A rule about who thinks.** Noah Vincent's Obsidian setup has Claude interview you to fill in `CLAUDE.md`, and ends with a warning worth keeping: if the AI writes all your permanent notes, the knowledge base holds its thinking, not yours. Let it surface and connect; you synthesise and decide [S:2029222820257935369].

All three make big promises: answers “with a citation”, a system that “gets smarter automatically”, even “perfect memory”. Treat those as hypotheses. Bober, for instance, says that when the information isn't there the agent reports a failure rather than hallucinating [S:2078784709253841039]. That's exactly the kind of claim today's lab tests.

> **Where the metaphor fails.** A herbarium specimen is fixed: nobody can quietly re-press the plant, and the original label stays legible for the next taxonomist. Agent memory is **rewritten by the agent**. Each `/process` run, each summary, each Mem0-style update is a model deciding what to keep, merge or delete, so an early misreading can be stored, cited back as evidence, and reinforced every time it's retrieved. Compaction is worse: it's a summary of a summary, with no voucher to return to. Keep raw inputs (the inbox originals, the full transcripts) archived, never let the agent delete, and audit the notebook with questions whose answers you know.

## 🛠 Lab: a field notebook with a recall test (15 min)

This is your **Unit 7 build**: the capstone's memory, a notebook the agents can read and cite, sitting next to the pack search you built in m20–m21.

**Part A (3 min, phone OK).** Write **10 recall questions** about papers or projects you know well: 8 whose answers will be in the notes you add today, and 2 that *won't* be (e.g. a detail you deliberately leave out). Write the correct answers too. This is your answer key.

**Part B (12 min, at a computer).** Gather raw material: your m14 paper summaries (`~/learn-ai/labs/m14/results/`), plus a few paragraphs of your own notes on 3 to 5 papers or field sites, pasted into text files. Create the folder and start Claude Code **inside it** (`mkdir -p ~/learn-ai/capstone/notebook && cd ~/learn-ai/capstone/notebook && claude`), so its own `CLAUDE.md` and commands load, then paste:

```text
Work only inside this folder, ~/learn-ai/capstone/notebook.
1. Create folders inbox/, papers/, species/, methods/, sites/, archive/ and root files decisions.md
   and LEARNINGS.md. Copy my raw notes (paths below) into inbox/ unchanged.
2. Write CLAUDE.md as the map: what each folder holds; one topic per file named for its content
   (lower-case-with-hyphens.md); each note starts with a one-line bold summary and ends with a
   Links section; never delete anything (move to archive/); keep my wording, don't rewrite my
   opinions; when answering, cite every note used with the supporting line; if the notes don't
   answer, reply exactly "Not in my notes" and stop.
3. Create two commands in .claude/commands/:
   - process.md: for each inbox file, split it into one-idea notes in the right folder, add 2-4
     links to related notes, then move the original to archive/inbox_processed/.
   - ask.md: answer $ARGUMENTS using ONLY the notes: answer in 3-6 sentences, then evidence
     (note path + supporting line), then disagreements between notes, then what the notes don't cover.
4. Run /process. Show me the resulting tree and two example notes.
Raw notes: [list your file paths]
```

Read two notes. Fix anything the agent got wrong *by hand*, so the notebook holds your thinking. Then run the recall test:

```text
Write recall_test.py: for each of my 10 questions (in questions.txt, with answers in key.txt), run a
headless call (`claude -p`) from this folder that says "Follow .claude/commands/ask.md to answer: <Q>".
Save each answer. Then show me a table: question, expected, answer, cited notes, and whether every
cited note path exists and contains the quoted line (check that in code). Leave a column for my
verdict: correct / wrong / correctly-refused / hallucinated.
```

**What to check**

- Fill in the verdict column yourself. Score: correct out of 8, and correctly refused out of 2. A confident answer to an uncovered question is the failure that matters most.
- Did any answer cite a note path that doesn't exist, or quote a line that isn't in the note? Your code check catches it; that's a citation hallucination.
- If a note was wrong after `/process` and you fixed it, did the fix change an answer? That's memory being rewritten, now by you, deliberately.
- Next step for later (not today): once the notebook passes about a hundred notes, give `/ask` your m21 hybrid search as a tool instead of relying on the map alone.

## 🧠 Self-check

**Q1. Name the three layers of agent memory and one weakness of each.**
A: Working context (limited, wiped between sessions, early instructions get lost as it fills); compaction (lossy summaries that get lossier with repetition and can drop mid-conversation instructions); external memory (only as good as what's written and how it's found, and it can store and reinforce errors).

**Q2. What did CMU's compaction story teach about evaluating memory?**
A: A compaction method that cost nothing on a benchmark still caused real failures (repeating the same pull request, forgetting mid-conversation instructions) because the benchmark didn't represent those situations. Memory needs realistic tests, not just benchmark scores.

**Q3. What does MemGPT borrow from computer operating systems, and what did Mem0 add?**
A: A memory hierarchy: a small, fast working context inside the window and a large, slow external store, with reads and writes made by the model's own tool calls. Mem0 added updating and deleting stored facts when new information contradicts or replaces them.

**Q4. Why “one topic per file, named for its content” in a second brain?**
A: The agent finds things through the map and filenames, so a descriptive name and a single topic make the right file easy to locate and cite; mixed files and names like `note-12.md` hide information and invite wrong retrievals.

**Q5. Why can't you treat agent memory like a herbarium?**
A: A herbarium specimen is fixed and checkable; agent memory is rewritten by the agent, so misreadings can be stored, cited and reinforced, and summaries of summaries have no original to return to. Keep raw inputs archived, forbid deletion, and audit with known-answer questions.
