## 🌿 The ecology hook

Touch a hot stove and your hand is moving before you've noticed the pain. A spinal reflex arc handles the routine, urgent decision in milliseconds, and the cortex hears about it afterwards. Nervous systems are layered: cheap, fast circuits for stereotyped stimuli, and expensive deliberation for the rest.

Your agent isn't layered yet. Every decision, from “which file next?” to “is this task hard?”, goes to the same model at the same price. Today you'll add a reflex layer: a **router** that decides which model (or which path) a task needs, and only wakes the cortex when it has to.

## 📖 Concept: send each task to the cheapest model that can do it

### The case for routing, with numbers

LangChain built a router for Open SWE, their internal coding agent, after their model spend kept climbing [S:2105704739585565066]. Their method is a template:

1. **Understand the tasks.** From a week of traces, they labelled requests by type (new features 22%, bug fixes 17%, tests or no-op runs 16% …) and found complexity varied widely, using cost and turn count as rough proxies [S:2105704739585565066].
2. **Understand the models.** Using a public intelligence-vs-cost benchmark, they picked three tiers on the cost-quality frontier: *fast*, *balanced* and *performance* [S:2105704739585565066].
3. **Build the router in the harness.** It has three parts: a base prompt (“pick the least expensive model likely to complete the task”), plain-language criteria for each tier, and a classifier model. It runs once, on the first message of a thread, and that model is used for the whole thread [S:2105704739585565066].
4. **Track outcomes.** Run offline evals on a fixed dataset, or an A/B test on live traffic. They used merged pull requests as the main success metric, plus thumbs up/down [S:2105704739585565066].

Their A/B test against “always use the strongest model”, over 973 threads [S:2105704739585565066]:

| | Routed | Always strongest |
|---|---|---|
| Threads ending in a merged PR | 29.2% | 27.3% (p = 0.49: no measurable difference) |
| Median cost per thread | $0.94 | $2.61 (64% less when routed) |
| Where routed threads went | 56% balanced · 34% fast · 10% performance | n/a |

The cost ladder between tiers was steep, about a 30-fold spread in median cost from fast to performance. And the opposite experiment, routing everything to the fast tier, was stopped within a day because engineers complained about the quality [S:2105704739585565066]. Routing isn't “use the cheap model”. It's “use the *right* model”.

### Why the router lives in the harness, and picks once

The router needs the same task context the harness already assembles, which a generic gateway doesn't have [S:2105704739585565066]. And it picks **once per thread** for a reason you met in m04: switching models mid-session throws away the prompt cache, so the new model re-reads everything at full price [S:2105704739585565066], [S:2104635196910030894].

### Decision models: a reflex that returns probabilities

A newer idea pushes this further. Many calls in an agent don't produce any text a person reads. They're **decisions**: which tool next, is this safe to run, is this diff ready. A widely shared “decision layer” guide argues these should go to a small model that returns typed answers with calibrated probabilities instead of generated text. It suggests starting with the router (high volume, low stakes), defining the answer schema first, feeding the confidence into control flow (confident answers pass, uncertain ones go to a fallback), and running safety checks in **shadow mode** before letting them gate anything [S:2106706177304240191]. (Its claim that 70–90% of agent calls are decisions comes with no measurement. Treat it as a hypothesis.)

Kev, from m03, is an open example of such a model. Its README advises the same pattern: let code route the confident cases and send the rest to a person, after testing the threshold on your own data [S:2101715352258232539]. The same post describes a Claude Code setup where a decision model runs inside hooks before prompts, before shell commands, and before the agent stops, and only escalates uncertain cases to a stronger “advisor” model [S:2106706177304240191].

### Honest results from people who tried

A checklist of ten open-source decision-layer projects is useful mainly because some of their READMEs report failures [S:2107578571124588977]:

- **jev-skill-router** ran in shadow mode for a week on its author's own sessions: 1,242 decisions and 539 skill suggestions, of which only about 5% were followed by the agent. The author removed it [S:2107578571124588977]. The reason: the main model already saw every skill description, so the router was a weaker second opinion.
- **codex-jev-router** found its routed sub-agents 27.2% cheaper than one fixed setting, but 69.7% *more* expensive than simply running one strong agent at high effort. It no longer recommends routing [S:2107578571124588977].
- **jev-belay**, a Stop hook that blocks unverified “done” claims, reports measured accuracy on 100 labelled stops [S:2107578571124588977]. Note that it's a *verification* job, not a routing one.

The lesson isn't “routers don't work”. It's that **a router is a hypothesis you have to evaluate**, against the right baseline.

```text
task ──► [ reflex: classifier ] ── tier + confidence ──► confidence ≥ threshold? ── yes ──► model for that tier
                                                                               └── no ───► escalate one tier up
          (once per task; log every decision; score against outcomes)
```

> **Where the metaphor fails.** Reflex arcs were tuned by selection over millions of generations, and a misfiring reflex usually hurts in a way the organism notices. A router is only as good as the labelled examples and evals behind it, and **misroutes fail silently**: an under-powered model hands back a plausible but worse answer, and nothing flinches. A reflex also never needs re-tuning because a new species of stove came out. Routers do, every time the models change.

## 🛠 Lab: give your harness a reflex (15 min)

**Step 1 (4 min). A labelled task set.** In `~/learn-ai/capstone`, paste into Claude Code or Codex:

```text
Create harness/route_tasks.jsonl: 20 tasks my agent.py could do over ~/learn-ai/labs (read-only questions about the files).
Mix: 8 trivial lookups (e.g. "which folder has the most files?"), 8 moderate (explain one script), 4 hard
(compare all scripts and find a bug or inconsistency). Fields: id, task, my_tier (fast | balanced | strong) — your best guess,
which I will correct. Show me the file and wait.
```

Correct `my_tier` where you disagree. These labels are your offline eval set, so they're yours to own.

**Step 2 (7 min). Build and score the router.** Paste:

```text
Create harness/router.py (standard library only) with two routers that each map a task to fast | balanced | strong
plus a confidence between 0.5 and 1:
1. rules_router(task): keyword and length heuristics.
2. model_router(task): one headless call to the CHEAPEST model (claude -p with the --model alias for the smallest model
   your CLI accepts; check claude --help; or the equivalent for codex exec). Base prompt: "pick the least expensive tier
   likely to complete the task", plus one line of criteria per tier. Reply JSON {"tier":..., "confidence":...}.
Then write harness/eval_router.py: run both routers on route_tasks.jsonl (one call per task for the model router),
compare with my_tier, and print a table: agreement %, UNDER-routes (tier weaker than mine, the dangerous error),
OVER-routes (wasted cost), and an illustrative cost using relative units fast=1, balanced=15, strong=30.
Also print the agreement among only the model router's answers with confidence >= 0.8.
Save every decision to harness/router_log.csv. Run it and show me the table.
```

**Step 3 (4 min). Wire it in.** Paste:

```text
Add --tier auto|fast|balanced|strong to harness/agent.py. With auto, call the model_router ONCE at the start of the task;
if its confidence < 0.7, escalate one tier. Use the chosen --model for every turn of that task (never switch mid-task,
to protect the prompt cache). Append task, tier, confidence, turns used and seconds to harness/router_log.csv.
Run three tasks from route_tasks.jsonl (one per difficulty) with --tier auto, show the log, and commit as "harness v1: router".
```

**What to check**

- How many **under-routes** did each router make? One under-route on a hard task can cost more in rework than many over-routes save.
- Did the model router's high-confidence answers agree with you more often than its low-confidence ones? If so, the confidence carries information (m03), and the escalation rule is earning its keep.
- Is the rules router good enough? If it matches the model router, use the free one. That's the “simplest thing that works” rule from m09.
- **Unit 3 build:** `harness/agent.py` now has tools, a boundary, a turn cap, a log and a router, in a little over 100 lines. Later units add a verifier and memory to this same file.

## 🧠 Self-check

**Q1. In LangChain's A/B test, what happened to quality and cost when they routed instead of always using the strongest model?**
A: Quality showed no measurable change (29.2% vs 27.3% of threads ended in a merged PR, p = 0.49), while median cost per thread fell 64% ($0.94 vs $2.61). Most threads went to the balanced and fast tiers.

**Q2. Why did their router pick a model once per thread instead of on every turn?**
A: Switching models mid-thread discards the prompt cache, so the new model re-reads the whole history at full price. That can wipe out the savings, and routing per turn also adds a classifier call on every turn.

**Q3. What are the three parts of their router?**
A: A base prompt (pick the least expensive model likely to complete the task), plain-language criteria for each tier, and a classifier model that reads the request and picks a tier.

**Q4. Why are under-routes worse than over-routes, and why are they hard to notice?**
A: An under-route gives a hard task to a model that can't do it well, which costs rework or ships a worse result. Over-routes only waste money. Under-routes fail silently, as plausible but worse answers, so you only see them if you track outcomes.

**Q5. Two decision-layer projects removed or stopped recommending their routers. What's the general lesson?**
A: A router is a hypothesis that must be evaluated against the right baseline, such as one strong agent or the main model's own choice. Gains on a weak baseline, or on scripted examples, may vanish in real sessions.
