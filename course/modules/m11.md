## 🌿 The ecology hook

Homeostasis is a loop with a sensor. Blood glucose rises, the pancreas detects it, insulin is released, and glucose falls back toward the set point. Density-dependent regulation is the same shape at the population scale: crowding feeds back on birth and death rates. What makes these loops work isn't the effector. It's the **sensor** that compares the current state with a target, and a response that stops when the target is reached.

Unit 4 is about the flows of work through your system. It starts with the smallest flow: a loop that does a piece of work, **checks it**, and goes round again until the check passes, or until it should give up.

## 📖 Concept: loop on evidence, not on confidence

### A loop is a check that can fail

The “Loops and Graphs” course strips the idea to four parts: **produce, check, correct, repeat until green** [S:2091515787366306154]. Its central claim is that the check is the whole thing. Without something that can fail the work while you're out of the room, you don't have a loop, just a scheduler. So write the check first, in a form a program could evaluate [S:2091515787366306154]:

```text
GREEN         the test suite exits 0
GREEN         every claim carries a source line
GREEN         the diff touches only files listed in the plan

NOT A CHECK   the output looks good
NOT A CHECK   the model says it is confident
NOT A CHECK   no errors were raised
```

The last line catches careful people: the absence of an error isn't evidence of correctness. A loop built on it confidently repeats a mistake until the budget runs out, with a clean log all the way [S:2091515787366306154]. An article quoted in the Claude Code podcast post compresses this into one rule: **do not loop on confidence, loop on evidence**. “The agent says it is done” isn't a stopping condition. “The tests pass, the links resolve and the schema validates” is [S:2106826633390772253].

### The loop contract

Gyomei's agent-architecture guide combines Addy Osmani's emphasis on persistent state with OpenAI's exit conditions and human-approval rules into a six-line **loop contract** [S:2098057823930155319]:

```text
job:       Classify new CI failures and draft fixes for deterministic bugs.
trigger:   Every weekday at 08:00.
state:     Read and update STATE.md.
verifier:  Run npm test and npm run lint. Reject on failure.
stop:      Stop after 3 attempts or 20 minutes.
approval:  Never merge, deploy, or edit auth or payments without review.
```

Each line removes one failure mode. The state file stops tomorrow's run repeating today's work. The verifier rejects bad work without you. The stop line caps retries and spend. The approval line keeps irreversible actions with a person [S:2098057823930155319]. Use **executable values** (“npm test”, “3 attempts”, “never merge”), not “check quality” or “until done”. And the test of readiness: if you can't fill the verifier line with a command or a deterministic rule, keep the task as a manual prompt [S:2098057823930155319].

The podcast article's anatomy adds two lines worth borrowing: a **goal** that is a specific state, not “keep improving”, and **feedback**, a compact description of *why* the evidence failed, handed to the next attempt [S:2106826633390772253].

### Stopping rules and budgets

- **Cap attempts.** The Loops and Graphs course says to cap a unit at three corrections. If it fails three times, the problem is in the plan that produced it, and the loop can't see the plan [S:2091515787366306154].
- **Escalate, don't spin.** OpenAI's guide names exceeded failure thresholds and high-risk actions as the two main triggers for handing control back to a human [S:2098057823930155319].
- **Remember on disk.** Addy Osmani's loop-engineering essay puts a memory file at the centre: the model forgets everything between runs, so progress must live in a file, not in the context [S:2098057823930155319].
- **Split the maker from the checker.** The same essay notes that the model that wrote the code is too generous grading its own homework. Claude Code's `/goal` and Codex's equivalent keep going until a written condition holds, with a separate model judging whether it's done [S:2098057823930155319].

### Where the loop runs

You don't need new infrastructure. Claude Code's `-p` flag runs it non-interactively: one instruction in, one answer out, composable with pipes, scripts and scheduled jobs [S:2104402058963026288]. The same guide draws the line that matters for loops: an instruction in `CLAUDE.md` is a suggestion Claude can forget, while a **hook** always runs [S:2104402058963026288]. LangChain describes a stack of loops: the agent loop inside, a **verification loop** with a grader around it, an **event-driven loop** that fires on schedules or webhooks, and an outer **hill-climbing loop** that analyses traces to improve the harness itself [S:2106826633390772253].

Osmani's warning belongs on every loop you build: a loop running unattended is also a loop making mistakes unattended. “Done” is a claim, not a proof, and the faster a loop ships work you didn't read, the bigger the gap between what exists and what you understand [S:2098057823930155319].

> **Where the metaphor fails.** Homeostatic loops are continuous, cheap and refined by selection. The sensor was tested by every ancestor that survived. Agent loops are **discrete and paid per iteration**, and nobody has tested your sensor. If the verifier is broken, the loop can run forever, or worse, can “succeed” forever: a test that always passes, or an agent that edits the test to make it pass (m01's Goodhart's law, in a terminal). Biology rarely lets the effector rewrite the sensor. Your loop has to forbid it explicitly.

## 🛠 Lab: a fix-until-green loop with a cap (15 min)

**Step 1 (5 min). A broken analysis and an honest judge.** In `~/learn-ai/capstone`, paste into Claude Code or Codex:

```text
Create analysis/diversity.py with two functions, shannon(counts) and simpson(counts) (Simpson's 1 - sum p^2),
and deliberately plant THREE bugs: use log base 10 instead of natural log, crash on zero counts instead of skipping them,
and forget the "1 -" in Simpson. Create tests/test_diversity.py (unittest, standard library) with hand-checkable cases:
[10, 10] -> H' = ln 2 ≈ 0.6931, Simpson = 0.5; [5, 0, 5] gives the same; [1] -> H' = 0, Simpson = 0; plus one 4-species case
with the expected values worked out in a comment.
Then write loops/LOOP.md: a six-line loop contract (job, trigger: manual, state: loops/STATE.md,
verifier: python3 -m unittest discover -s tests, stop: 3 attempts or 10 minutes, approval: I review the final diff).
Run the tests now and show me that they FAIL on the buggy code. Do not fix anything.
```

Check one expected value yourself: for `[10, 10]`, is H′ really ln 2 and Simpson really 0.5? A judge you haven't checked is just another optimist.

**Step 2 (7 min). The loop.** Paste:

```text
Write loops/fix_until_green.py (standard library only), following loops/LOOP.md:
- Run the verifier. If it passes, write "GREEN" to loops/STATE.md and stop.
- Otherwise call a fresh headless agent (claude -p, or codex exec) with: the contract, the failing test output
  (last 60 lines), what previous attempts tried (from STATE.md), and the scope:
  "Edit ONLY analysis/diversity.py. Do not edit tests. Do not run git commands."
  Use your CLI's flag for allowing file edits without prompting (check --help) and allow nothing else.
- Before and after each attempt, compute a SHA-256 of tests/test_diversity.py; if it changed, restore it with
  git checkout, log "TAMPER" and count the attempt as failed.
- Append one line per attempt to loops/STATE.md: time | attempt | tests passed/failed | files changed | seconds.
- Stop after 3 attempts or 10 minutes total; on stop without GREEN, write "ESCALATE: needs human" with the last failure.
Commit the buggy version first, then run the loop and show me STATE.md and the final git diff.
```

**Step 3 (3 min). Break it on purpose.** Run the loop once more with a verifier that can't pass. Temporarily add a test expecting `shannon([10, 10]) == 99`. The loop must stop after 3 attempts with `ESCALATE`, not spin. Then remove that test and commit.

**What to check**

- STATE.md shows how many attempts it took. Did it go green within the cap?
- Read the final diff yourself (the approval line of your contract). Did it fix exactly the three bugs, and nothing else?
- Did any attempt trigger `TAMPER`? If so, you've just watched reward hacking happen in miniature.
- In Step 3, did the loop stop cleanly? A loop that can't give up isn't safe to schedule.

## 🧠 Self-check

**Q1. What makes something a loop rather than a scheduler, according to the Loops and Graphs course?**
A: A check that can fail the work without you present. Produce, check, correct, repeat until green. Without a check that can fail, you just have something running repeatedly.

**Q2. Why is “no errors were raised” not a valid check?**
A: The absence of an error isn't evidence of correctness: wrong output often runs without errors. A loop built on it can repeat a mistake until the budget runs out while every log line looks clean.

**Q3. List the six lines of the loop contract and the failure each prevents.**
A: Job (scope creep and vague work); trigger (when it runs); state (repeating yesterday's work); verifier (bad work getting through without you); stop (endless retries and spend); approval (irreversible actions without a human).

**Q4. Why cap attempts at about three instead of letting the loop keep trying?**
A: Repeated failure usually means the plan or the task specification is wrong, which the loop can't see. More attempts mostly burn tokens, so stop and escalate to a person with the evidence.

**Q5. Your loop always goes green on the first attempt. What should you suspect, and how do you test it?**
A: The verifier might be blind (always passing) or the agent might be editing the tests. Break it on purpose: feed it known-bad work or an impossible test and confirm it fails, and guard the test files (for example with a hash check).
