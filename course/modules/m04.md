## 🌿 The ecology hook

Every habitat has a carrying capacity, *K*. Below it, adding individuals is cheap. Near it, crowding starts to hurt everyone: resources thin out, interference rises, and the whole population performs worse.

A model's **context window** is its habitat: the tokens it can hold at once. Everything has to live there: your instructions, the files it read, every command's output, every “no, I meant…”. Unit 1 was about what the model *is*. Unit 2 is about the environment you build around it, starting with the most limited resource of all.

## 📖 Concept: the window, the bill, and the squeeze

### Every turn re-reads everything

A chat feels like a conversation, but the model has no memory between calls. On each turn, the whole conversation so far is sent again and read again from the top. Ruben Hassid's guide puts it in plain terms: every message, Claude re-reads your whole conversation, every message and every file, then thinks, then writes [S:2107712638381941071].

The CMU agents course does the arithmetic. If each agent step adds a few tokens and every call re-processes the full history, the total number of tokens processed grows **quadratically** while the history only grows linearly [S:2104635196910030894]. Graham Neubig also broke down what actually fills an agent's context, using 1,500 sessions of the OpenHands coding agent (about 78,000 tokens per session on average) [S:2104635196910030894]:

| What filled the context | Share |
|---|---|
| Tool results (file contents, command output) | 37% |
| System prompt and tool descriptions | 23% |
| Tool calls | 20% |
| User messages | 9% |
| Model reasoning | 9% |
| Model replies to the user | 2% |

The model's own words are the smallest slice. Most of the habitat is taken up by what tools drag in, and by the standing instructions you load every time.

### Caching: why the prefix must not move

Providers soften the bill with a **prompt cache**: if the start of the request is *exactly* the same as last time, the work already done on it is reused, and it costs much less. Hassid notes that cached reading counts much less against your limits [S:2107712638381941071].

The catch is that the cache only works if the **entire prefix is identical** [S:2104635196910030894]. The CMU lecture lists the classic ways to break it:

- **Changing the system prompt every step**, for example by putting the current date and time in it. Put changing information at the *end* instead [S:2104635196910030894].
- **Switching models mid-session.** Each model has its own cache, so the new model re-reads everything at full price [S:2104635196910030894]. Hassid gives the same rule to chat users: pick a model and don't switch mid-chat [S:2107712638381941071].
- **Taking a long break.** Providers evict cached prefixes after a while. The lecturer recalls Anthropic's default as about five minutes, with a longer paid option, though he flags he may be out of date [S:2104635196910030894]. Hassid's practical version: before you leave a long chat, ask for a ten-line summary, and paste it into a fresh chat when you come back [S:2107712638381941071].

### Bigger windows aren't better habitat

Being able to accept a million tokens doesn't mean being able to *use* them. In “needle in a haystack” tests, a fact buried in ever-longer text gets missed more often as the context grows [S:2104635196910030894]. Students in the CMU class named the symptom straight away: the agent forgets. One example from the lecture was a user who said “do not delete this” mid-session, and the agent later deleted it [S:2104635196910030894]. LangChain calls the general effect **context rot**: models get worse at reasoning as the window fills [S:2098057823930155319]. The Claude Code guide gives the same warning from the user's side. A full context makes it harder to separate signal from noise, and early instructions start to slip [S:2104402058963026288].

OpenAI's harness-engineering team reached the same conclusion from the instructions side: **context is a scarce resource**, and a giant instruction file crowds out the task, the code and the relevant docs [S:2098057823930155319]. That's tomorrow's module.

### Compaction: density-dependent regulation, with losses

When the window gets close to full, harnesses **compact** it: older history is squeezed into a summary so work can continue. The CMU lecture describes the usual policy [S:2104635196910030894]:

- **Trigger:** a token threshold, a hard provider limit, or a manual `/compact`.
- **Protect** the anchors (the first instructions of the session) and **keep** the recent tail verbatim.
- **Summarise** the middle, sometimes into a required structure.
- **Store** the full evidence somewhere it can be re-read later. A CLI agent usually keeps the full history on disk.

The harness source-code study found this threshold-triggered compaction in seven of eleven production harnesses. For example, Claude Code fires a fixed buffer below the limit, and Gemini CLI compacts at 50% while preserving the last 30% [S:2106479763636302271].

Compaction is lossy, and its failures are sneaky. The OpenHands team built a compaction method that didn't lower their benchmark score at all. In real use it made the agent forget it had already opened a pull request, so it opened the same one five times. It also dropped instructions the user had given mid-conversation, because the benchmark only ever had a single user message [S:2104635196910030894]. Each round of compaction also loses a bit more than the last [S:2104635196910030894].

### Habits that keep the habitat healthy

| Habit | Why it works | Source |
|---|---|---|
| One task per session; `/clear` between tasks | Nothing stale is re-read on later turns | [S:2104402058963026288], [S:2107712638381941071] |
| Put all your asks in one message | Three messages means three full re-reads | [S:2107712638381941071] |
| Plan first, then build | A wrong path costs a whole context of tool output | [S:2104402058963026288] |
| Keep the instruction file short | It's re-read on every turn | [S:2106712905001365608], [S:2107712638381941071] |
| Hand big searches to a subagent | It works in its own context and returns only a summary | [S:2104402058963026288] |
| Pin rules that must survive | Summaries can drop them; a file the agent re-reads can't | [S:2106479644354474463] |
| Check `/context` and `/usage` | You can't manage what you don't measure | [S:2104402058963026288], [S:2107712638381941071] |

On that last-but-one row: a harness-design article cites one (single-author, unreviewed) study in which policy violations went from zero, with the rule in full view, to 30% after compaction, but stayed at zero when the rule survived the summary [S:2106479644354474463]. Treat the number as a hint. The fix, a pinned rules file, costs almost nothing.

> **Where the metaphor fails.** Food is eaten once. Context is **re-read in full on every turn**, so each token you add is paid for again and again for the rest of the session. A crowded context also fails differently from a crowded habitat. Nothing starves. Instead the model gets *distracted*: it pays attention to the wrong things, forgets early instructions, and makes careless mistakes. And raising *K* (a bigger window) doesn't raise the quality of the habitat.

## 🛠 Lab: measure your agent's carrying capacity (15 min)

**Part A (3 min, phone OK).** Do the arithmetic by hand. An agent session has a 5,000-token system prompt and adds 3,000 tokens per turn. Without caching, how many tokens are read in total over 20 turns? (Sum of 5,000 + 3,000 × t for t = 1 to 20.) How big is the context on the last turn? Write both numbers in your notes and compare them.

**Part B (12 min, at a computer, Claude Code).** Use any folder with a few files, for example `~/learn-ai/labs`.

1. Start `claude` in that folder and type `/context`. Note the total and the biggest categories. Then type `/usage` and note where you are.
2. **The crowded session.** Paste these one at a time:

```text
Read every file under this folder and summarise each one in two lines.
```

```text
Now explain how the m01 script works in detail, then the m02 script, then the m03 script.
```

```text
Compare all three scripts and list ten ways to improve them. Don't change any files.
```

3. Type `/context` again. Note the new total, and how much of it is tool results (the file contents it read).
4. **Probe for rot.** Ask: *“What was the first instruction I gave you in this session, word for word?”*
5. Type `/compact`, then `/context`, then ask the same probe question again. What survived the summary?
6. **The scoped session.** Type `/clear`, then paste:

```text
Read only ~/learn-ai/labs/m02/sample_runs.py and tell me in three bullet points how it measures answer diversity.
```

Type `/context` once more. Write a 4-row table in your notes: start, crowded, after compact, scoped.

**Using Codex instead?** Type `/` in the Codex session to list its built-in commands, then use its status and compact commands for the same steps. (Background: command names differ between tools and versions. The habit is the same.)

**What to check**

- Part A: 730,000 tokens read in total, for a final context of only 65,000. That ratio is the quadratic growth in action.
- Was most of the crowded session's growth tool results? Compare with the OpenHands breakdown above.
- Did the probe answer stay accurate after `/compact`? If not, that's exactly the risk the OpenHands team hit.
- The scoped session should be a small fraction of the crowded one. That gap is what “one task, then `/clear`” buys you.

## 🧠 Self-check

**Q1. Why does an agent's token bill grow faster than the length of its conversation?**
A: Each call re-sends and re-reads the whole history, so the total tokens processed is the sum of all the context sizes along the way, which grows roughly quadratically with the number of turns. Caching makes repeated prefixes cheaper but doesn't change that shape.

**Q2. Name two things that break the prompt cache, and the fix for each.**
A: Changing the start of the prompt every step, such as a timestamp in the system prompt: put changing information at the end instead. Switching models mid-session: pick one model per session. (A long break also lets the cache expire: summarise, then start fresh.)

**Q3. In the OpenHands data, what took up the largest share of agent context?**
A: Tool results (37%), such as file contents and command output, followed by the system prompt and tool descriptions (23%). The model's replies to the user were only 2%.

**Q4. Why can a compaction method pass a benchmark and still fail in real use?**
A: The benchmark may not contain the situations compaction destroys. OpenHands's benchmark had single-turn tasks, so it never tested forgetting mid-conversation instructions or remembering that a pull request had already been opened. Real use did both.

**Q5. A rule like “never touch the production database” must survive a six-hour session. Where should it live?**
A: In a pinned file that the agent re-reads after every reset (and in the system prompt), not only in the chat history, where compaction can summarise it away.
