## 🌿 The ecology hook

Division of labour is one of the great inventions of social insects. Nurses, foragers, guards and undertakers each do one job, in one place, with the tools their body and age give them, and the colony gets more done than the same number of generalists would.

There's a second ecological force worth borrowing. Predators keep prey populations honest: the slow, the sick and the careless get culled, and what survives is fitter for it. A system with no predator drifts.

Today's agents use both ideas. **Subagents** are specialised workers with their own context and a restricted tool kit. And the most valuable specialist of all is the **adversary**: an agent whose only job is to find what the builders missed before anyone says “done”.

## 📖 Concept: specialists, teams and a predator

### A subagent is a worker with its own context window

In Claude Code, a subagent is a Markdown file with a short header (name, description, which tools it may use, which model, which permission mode) and a system prompt underneath. It starts with an **isolated context**, does its job, and returns only its result to the main conversation [S:2098057823930155319]. The Claude Code docs list when that's worth it:

- the task produces verbose output you don't want in your main context (test logs, documentation searches, log files);
- you want to **enforce tool restrictions or permissions**;
- the work is self-contained and can come back as a summary.

Stay in the main conversation for quick, targeted changes, back-and-forth work, and anything where several phases share a lot of context [S:2098057823930155319].

Restricting tools is the part people skip. A `tools` list is an allowlist: the docs' example gives a subagent only Read, Grep, Glob and Bash, so it can't edit or write files. A `disallowedTools` list does the reverse, removing tools from what it would otherwise inherit [S:2098057823930155319]. Gyomei's CI example builds a **reviewer** subagent exactly this way: read-and-search tools only, `permissionMode: plan`, and the instruction not to edit files or approve its own exceptions. The parent passes it only what it needs (the patch, the failure log, the test command) and gets back a verdict, the failed checks, evidence and required changes [S:2098057823930155319].

### Teams: when workers need to talk to each other

Claude Code also has experimental **agent teams**, off by default: a lead session coordinates teammates, each with its own context window, who can message each other directly and claim work from a shared task list [S:2105764769479455043]. The docs are clear about the cost and the fit:

- Teams use **significantly more tokens** than one session; cost scales with the number of active teammates [S:2105764769479455043].
- They fit research and review, separate new modules, cross-layer changes, and **debugging with competing hypotheses**. Sequential work, same-file edits and tightly dependent tasks are better done by one session or subagents [S:2105764769479455043].
- Start with **3 to 5 teammates**; three focused teammates often beat five scattered ones. Give each teammate a different set of files so they don't overwrite each other [S:2105764769479455043].

Short version from the docs: use subagents for quick, focused workers that report back; use teams when workers need to share findings and challenge each other [S:2105764769479455043].

### The predator: an adversary before “done”

```text
   lead / main session ──────────────── plans, merges
      │            │
   builder A    builder B   ← isolated contexts, own files
      │            │
      └─────┬──────┘
            ▼
   ADVERSARY (read-only)  wakes at three moments:
     1. before an interface or plan locks
     2. when the same error comes back twice
     3. before anyone says "done"
```

Two posts in the pack describe the same three moments. In a team setup, a dedicated adversary steps in before a contract locks (does the frontend payload match the backend schema?), when a test breaks twice (are we fixing the bug or hiding the symptom?), and before calling it done (what edge case did everyone overlook?) [S:2105764769479455043]. Claude Code's **advisor** tool builds the idea into one session: a stronger advisor model reads the whole conversation and tends to be consulted before committing to an approach, when an error keeps recurring, and before declaring a task done [S:2105040007127761242]. The docs add caveats worth knowing: the advisor is experimental, the timing is decided by the model rather than by rules, it may use more tokens, and on some plans using Fable as the advisor bills to usage credits [S:2105040007127761242]. You don't need it for today's lab; a read-only reviewer subagent gives you the same shape for free.

The underlying principle is older than any feature. The harness-engineering article quoted in the pack separates the **creator role** from the **reviewer role**: draft first without self-evaluation, then review as a skeptical senior reviewer against a specific checklist [S:2105764769479455043]. Asking the same model “are you sure?” in the same context tends to confirm its first answer [S:2105764769479455043].

### The echo-chamber trap

Hanako's course names the failure that ruins most multi-agent reviews. Give four auditors a **shared window** and they converge: the first writes a finding, the others read it, and all four reports centre on the same thing. “You paid four times for one opinion with three echoes” [S:2091515787366306154]. The fixes:

- **One lens per worker, each in its own context** [S:2091515787366306154]. The agent-teams docs do the same for parallel code review, giving teammates distinct domains such as security, performance and test coverage [S:2105764769479455043].
- **Split along the right dimension.** Cut a repository by folder and four workers audit the same three files; cut by blast radius and each sees something the others can't [S:2091515787366306154].

> **Where the metaphor fails.** Real castes differ in genes, age, development and experience, so their errors are partly independent. Cloned agents share the same weights, the same training and often the same context, so they share the same blind spots. Put five of them in one window and you get conformity, not division of labour. And a predator culls the weak automatically; an adversary agent only “culls” what its prompt and tools let it see. Diversity has to be designed in: separate contexts, different lenses, deterministic checks, and occasionally a different model.

## 🛠 Lab: a read-only reviewer that knows zeros are data (15 min)

You'll use the `fieldqa/` folder in your capstone repo from m13. (If you skipped it, ask your agent to create a tiny `fieldqa/clean_counts.py` with a `clean(rows)` function and tests first.)

**Part A (3 min, phone OK).** Write three review lenses for field count data that would each find different problems, e.g. *data semantics* (zeros, NA, units), *code correctness* (edge cases, types), *provenance* (raw files untouched, changes logged). These become the reviewer's checklist.

**Part B (12 min, at a computer).** Start Claude Code in your capstone repo root (`cd ~/learn-ai/capstone`), so it picks up the project's `.claude/` folder, and paste:

```text
Create a project subagent at .claude/agents/data-reviewer.md:
- description: "Read-only reviewer for changes to field-data cleaning code. Use before any commit."
- tools: Read, Grep, Glob, Bash (Bash only to run the tests and git diff); permissionMode: plan
- system prompt: review the current git diff against three lenses: (1) data semantics: zeros,
  missing values, units, species-name variants; (2) code correctness and edge cases;
  (3) provenance: nothing under data/raw/ changed, rejected rows are reported not silently dropped.
  Never edit files. Return: verdict (pass/fail), findings (lens, file:line, evidence, severity),
  and required changes.
Show me the file and wait for my OK.
```

Then seed a realistic bug on purpose. Paste:

```text
Change clean() in fieldqa/clean_counts.py so that it also removes rows where count == 0, "to tidy the dataset". Add a passing
test for that behaviour. Do not commit.
```

(An ecologist will spot the problem: a zero count is a real observation, an absence, and dropping it biases every abundance estimate.) Now run the reviewer in its own context:

```text
Use the data-reviewer subagent to review the current uncommitted change. Then append one line per
finding to review_log.csv with columns: date, change, lens, finding, severity, true_or_false_positive
(leave the last column blank for me to fill).
```

**What to check**

- Did the reviewer flag the dropped zeros under the data-semantics lens? If not, your lens wording was too vague: tighten it and run again. That's prompt engineering with an eval attached.
- Ask the reviewer to fix the bug itself. It should refuse or be unable to, because it has no edit tools and runs in plan mode. If it *can* edit, your restriction failed: find out why.
- Fill in the `true_or_false_positive` column yourself. False positives cost your attention; misses cost your data. Keep this log: the capstone's eval suite (Unit 8) will start from it.
- Revert the seeded bug (`git checkout -- fieldqa`) before moving on.

Codex users: run the review as a separate `codex exec` call in a fresh session, with the reviewer prompt above and Codex's read-only sandbox mode if your version offers it; the point is a separate context and no write access.

## 🧠 Self-check

**Q1. Give two good reasons to use a subagent instead of the main conversation, and one reason not to.**
A: Good reasons: the task produces verbose output you don't want in your main context, you want to enforce tool restrictions, or the work is self-contained and can return a summary. Not: quick targeted changes or iterative back-and-forth work where phases share a lot of context (and a fresh subagent needs time to gather context).

**Q2. What are the three moments when an adversary or advisor is most useful?**
A: Before committing to a plan or locking an interface, when the same error comes back (are we fixing the cause or hiding the symptom?), and before declaring the task done.

**Q3. Four reviewers share one context window and all report the same issue. Why is that a problem, and what's the fix?**
A: They converged: the first finding anchored the rest, so you paid for four reviews and got one opinion with three echoes. Give each reviewer its own context and a distinct lens (or split the work along a dimension where each sees something different).

**Q4. When do Claude Code's docs say an agent team is better than subagents, and what does it cost?**
A: When workers need to share findings, challenge each other and coordinate on their own: research and review, competing-hypothesis debugging, separate modules. It costs significantly more tokens (each teammate has its own context, so cost scales with team size) plus coordination overhead.

**Q5. Why isn't a team of cloned agents like a caste system?**
A: Castes differ genuinely, so their errors are partly independent. Cloned agents share weights, training and often context, so they share blind spots. Diversity must be designed in through separate contexts, different lenses, deterministic checks or different models.
