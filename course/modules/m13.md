## 🌿 The ecology hook

Think of a well-run field station. Data loggers record temperature every ten minutes whether anyone is awake or not. Technicians run the weekly transects from a written protocol. The −80 freezer has a key that only two people hold. Out-of-range readings get flagged automatically by the QA script before anyone looks at them. And the principal investigator doesn't check every quadrat: they sign off the **final dataset** before it's released.

That is the shape you want for agents. Routine work runs unattended inside written rules, mechanical checks catch errors without you, and your signature goes on one thing only: the irreversible last step. In m11 and m12 you built loops and graphs. Today you give them the field-station rules: **instructions, permissions, hooks and headless runs**, and you move yourself to the end of the line.

## 📖 Concept: four ways to bound an agent

### 1. Instructions are suggestions; hooks are physics

You already know `CLAUDE.md` (m05): a file the agent loads every session with your conventions and “never do this” rules. The Claude Code guide in the pack makes a distinction that is worth memorising: an instruction in `CLAUDE.md` is a suggestion the model can forget, while a **hook** always runs [S:2104402058963026288]. Hooks are commands that fire automatically at fixed moments: before a tool is used, after it, or when the agent finishes replying. Typical uses are formatting a file after every edit, blocking writes to a sensitive folder, or running the tests when the agent says it's done [S:2104402058963026288].

The harness-engineering article calls this the **dual-encoding rule**: state the rule in words so the model understands the goal, then add a mechanical gate that blocks execution if the rule breaks. If the agent must not delete files, say so, and also make sure the delete command fails [S:2105764769479455043].

### 2. Permissions: what it may do without asking

Claude Code asks before editing files or running commands by default. You can switch modes (normal, accept-edits, and **plan mode**, which only reads and analyses until you approve a plan), and you can write permanent rules in the project's `.claude` settings: what's always allowed, what needs confirmation, and what's blocked, such as reading your secrets file [S:2104402058963026288]. The guide's advice is to **start strict** and add a command to the allow list only when it is safe and keeps interrupting you, so the setup grows with real trust [S:2104402058963026288].

In his talk, Claude Code's creator says making shell commands safe was one of the hardest parts: shell commands can change system state in unexpected ways, but approving every one by hand makes you unproductive. The answer was a tiered permission system where commands can be allow-listed or block-listed at different levels (personal, project, or company-wide policy that an individual can't override) [S:2106712905001365608].

The harness source-code study (arXiv 2609.00006) shows that the big coding agents have converged on a similar stack. Claude Code layers fast static hook rules, then a model-based permission classifier (allow / ask / deny), then an interactive dialog with you. Codex has four layers: an execution-policy file, lifecycle hooks whose event names are almost identical to Claude Code's (`PreToolUse`, `PostToolUse`, `Stop` and others), an LLM approval reviewer, and an operating-system sandbox. All the provider-built agents now ship a read-only planning mode [S:2106479763636302271].

### 3. Hooks in practice

A `PreToolUse` hook runs before a tool call and can block it. The Claude Code docs show a hook script that reads the proposed command as JSON on standard input and exits with code 2 to refuse a write [S:2098057823930155319]. A `PostToolUse` hook runs after the call, which makes it the natural place to run your tests after every edit. The test output then goes back to the agent as evidence, which is the “sensor” from m11's loop: the model writes, the sensor reports, the harness decides [S:2105764769479455043].

### 4. Headless runs: the agent without a conversation

`claude -p "<task>"` runs Claude Code non-interactively: it takes one instruction, works, prints the result and exits, so you can pipe it into other commands or put it in a scheduled job or CI pipeline [S:2104402058963026288]. (`codex exec "<task>"` is the Codex equivalent you used in m02.) Headless is where permissions stop being a convenience and become the whole safety story, because nobody is there to click “approve”.

Before you schedule anything, write its **loop contract**. Gyomei's version has six lines, each closing a specific failure: job, trigger, state file, verifier command, stop rule (attempts or minutes), and an approval line naming what it may never do without you. If you can't fill the verifier line with a command or a deterministic rule, keep the task manual [S:2098057823930155319].

### Where the human goes

```text
          routine work (unattended)                       you
 ┌────────────────────────────────────────────┐   ┌──────────────┐
 │ CLAUDE.md rules → permissions (allow/deny)  │   │              │
 │   → agent edits → PostToolUse hook: tests   │──▶│ read the diff │──▶ commit / merge
 │   → red? feed failure back (max 3 tries)    │   │  approve ONE │     (irreversible)
 │   → green + in scope → stop, print diff     │   │    thing     │
 └────────────────────────────────────────────┘   └──────────────┘
   blocked outright: push, delete, secrets, production data
```

Hanako's Loops and Graphs course puts the human **on one step, at the point of highest consequence and lowest reversibility**: approve the merge, not each intermediate output. A human in the middle of a graph becomes its slowest node [S:2091515787366306154]. Two more ideas from that course:

- **Gate on blast radius, not on confidence.** The model's confidence is the one input the model itself can influence. Sort work instead by how expensive a mistake is to undo: reversible and contained work can flow; wide but reversible work needs deterministic checks; hard-to-reverse work (deletions, migrations, anything touching production data) is a lane that **does not open**, which is different from a high threshold, because thresholds get adjusted [S:2091515787366306154].
- **Absence of an error is not evidence of correctness.** A loop whose “check” is “no errors were raised” will confidently repeat a mistake until the budget runs out [S:2091515787366306154].

OpenAI's practical guide gives the same two triggers for human intervention: exceeding a failure threshold (too many retries) and high-risk actions that are sensitive, irreversible or expensive [S:2098057823930155319]. And Gyomei adds a rule worth taping to your monitor: the completion condition reads the **gate status**. A message from the agent saying it's finished should never unlock a merge or deploy [S:2098057823930155319].

One caution about approval prompts themselves. A summary of the harness paper claims people approve the overwhelming majority of permission prompts they see; the exact figure isn't traceable, but the point stands: a prompt you always click through is a delay, not a control. Use prompts for the few things you'd genuinely stop for, and hard boundaries for everything else [S:2106479644354474463].

> **Where the metaphor fails.** A field assistant understands *why* the freezer key is restricted, and fills gaps in the protocol with judgement. An agent follows the **literal** permissions. If the rules forbid `rm` but allow `python`, nothing stops a Python one-liner that deletes the file; that isn't malice or cleverness, it's an optimiser finding the open path. Gaps in your rules get exploited by accident. That's why the hard lanes belong at the level that can't be worked around (deny rules, sandboxes, no credentials in reach), not in prose, and why you still read the final diff.

## 🛠 Lab: a field-QA repo that only asks for your signature (15 min)

**Part A (4 min, phone OK).** In your notes, sort these eight actions for a field-data pipeline into three lanes, **auto** (allow, checked by tests), **ask** (needs you), **closed** (never, regardless of confidence): (1) run the test suite, (2) edit `clean_counts.py`, (3) read `.env` with a database password, (4) `git commit`, (5) `git push` to the shared lab repo, (6) delete raw CSVs in `data/raw/`, (7) add a new Python dependency, (8) overwrite last season's published dataset. Compare with the lanes in the diagram, then keep the list: you'll encode it next.

**Part B (11 min, at a computer).** This is your **Unit 4 build**, and it becomes the field-data-QA corner of your capstone. Open a terminal **in your capstone repo** (`cd ~/learn-ai/capstone`, the git repo you created in m05; create it with `git init` first if you skipped that). Start **Claude Code** there in plan mode (press Shift+Tab until it says plan mode), and paste:

```text
This is my capstone repo (already a git repo; keep its existing map files). Put new code in fieldqa/.
Plan first, show me the plan, and wait for my approval before writing anything.
Build:
1. fieldqa/clean_counts.py (Python standard library only) with a function clean(rows) that takes a list
   of dicts {site, date, species, count} and returns cleaned rows: strip whitespace, lower-case species,
   reject rows whose count is not a non-negative integer, and report rejected rows with a reason.
2. fieldqa/tests/test_clean_counts.py with at least 6 pytest tests, including a negative count,
   a blank species and a count of "12.0".
3. fieldqa/CLAUDE.md: what the folder is, how to run its tests, and "never edit data/raw/".
4. .claude/settings.json at the repo root with permission rules: allow running pytest, git status,
   git diff and git add; deny git push, any rm command, and reading .env files.
5. A PostToolUse hook in the same settings file that runs the fieldqa tests after every Edit or Write
   and shows the result to you, the agent. Use the current Claude Code hooks format; check the docs or
   /hooks rather than guessing, and tell me which version you followed.
6. Do not run git init and do not commit; I will commit myself after the tests pass.
After building, prove each control works: make one test fail on purpose and show me the hook output,
then try `git push` and show me that it is refused. Then revert the deliberate failure.
```

When that's done, exit and run one task **headlessly** from the same folder (Codex users: use `codex exec` and ask Codex to set up its own equivalent rules first):

```text
claude -p "Add a function flag_duplicates(rows) to fieldqa/clean_counts.py that returns rows sharing the same site, date and species, plus tests for it. Run the fieldqa tests until they pass, at most 3 attempts. Do not commit. Finish by printing git diff --stat and the test summary."
```

**What to check**

- The hook really fired during the build: you saw test output appear after an edit without asking for it. If not, the hook isn't wired; ask the agent why.
- `git push` was refused by a rule, not by the agent “deciding” not to. Ask: *“Was that blocked by a permission rule or by your own judgement?”*
- The headless run either finished green or stopped after three attempts. If it stalled on a permission it wasn't allowed, that's the lab working: note which permission, decide which lane it belongs in, and add it only if it's **auto**.
- Now do your one job. Read `git diff`. If it's in scope and the tests pass, commit it yourself (first the build, then the headless change). Those commits are the only steps you approved today.

## 🧠 Self-check

**Q1. Why does the Claude Code guide say a hook is stronger than a line in CLAUDE.md?**
A: CLAUDE.md is loaded as instructions, which the model can forget or skip under load. A hook is executed by the harness at a fixed moment every time, regardless of what the model decides. That's the dual-encoding rule: words for intent, a mechanical gate for enforcement.

**Q2. Your headless job's agent prints “All done, everything works!” What should decide whether the change can be merged?**
A: The gate status: deterministic evidence such as the test exit code and a diff that stays inside the planned files, read by the harness. The agent's message is not evidence; a completion message should never unlock a merge.

**Q3. Why gate on blast radius rather than on the model's confidence score?**
A: Confidence is the only input the model itself can influence, so it's the weakest. Blast radius (how hard the mistake is to undo) is a property of the action. Contained, reversible work can flow automatically; hard-to-reverse actions get a lane that never opens, which unlike a threshold can't drift.

**Q4. You deny `rm` but the agent deletes a file using a Python one-liner. What went wrong, and what's the better fix?**
A: The rule was written against one command, not against the outcome. Agents follow literal permissions, so gaps get exploited by accident. Better fixes act at a level the agent can't route around: protect the folder (deny writes to `data/raw/`, or make it read-only), use a sandbox, and keep backups under version control.

**Q5. Where should the one human approval sit in an unattended workflow, and why not in the middle?**
A: At the step of highest consequence and lowest reversibility, such as the commit, merge or data release. A human approving intermediate steps becomes the slowest node, and the whole graph runs only as fast as a person reading.
