## 🌿 The ecology hook

Ask a non-biologist how an ant colony works and you'll hear about a queen giving orders. You know better. The queen mostly lays eggs; the colony's work is coordinated from the bottom up. Foragers lay pheromone on the trail they used, others follow the strongest trail, and the trail itself becomes the message. Grassé called that **stigmergy**: coordination through traces left in a shared environment rather than through a boss.

Both pictures turn up when people wire several AI agents together. Some systems use a **manager**: one agent decides who does what and stitches the answers together. Others use **handoffs**: agents pass the work, and the conversation, to whichever peer is the right specialist. And many use a shared “whiteboard” that every agent reads and writes, which is stigmergy by another name. Today you'll learn the two main topologies, how to choose between them, and the most important option of all: not going multi-agent.

## 📖 Concept: who holds the thread?

### Start with one agent

OpenAI's practical guide is blunt: maximise a single agent's capabilities first. More agents give a tidy separation of concerns, but they add complexity and overhead, and often one agent with tools is enough [S:2098057823930155319]. The guide gives two signals that it's time to split:

- **Complex logic.** The prompt has grown so many if-then branches that templates no longer scale.
- **Tool overload.** The problem is not the number of tools but their **overlap**. Some systems handle more than 15 well-defined, distinct tools, while others struggle with fewer than 10 that look alike. Try clearer names and descriptions first; split only if that doesn't help [S:2098057823930155319].

### Two topologies

The same guide describes multi-agent systems as graphs with agents as nodes, and the two common patterns differ in what the **edges** mean [S:2098057823930155319]:

```text
 MANAGER (agents as tools)                 DECENTRALISED (handoffs)
        user                                    user
         │                                       │
     ┌───▼────┐   tool call   ┌──────────┐   ┌───▼────┐ hand off ┌─────────┐
     │manager │──────────────▶│ worker A │   │ triage │─────────▶│ orders  │──▶ user
     │        │◀──────────────│          │   └────────┘          └─────────┘
     │        │──▶ worker B   └──────────┘   (control and the conversation move;
     │        │──▶ worker C                    the first agent steps out)
     └───┬────┘
         ▼  one voice back to the user
                                             SHARED BOARD (stigmergy)
                                             agents read/write one state object;
                                             the board, not a boss, carries the message
```

- **Manager pattern:** a central agent calls specialist agents the way it would call a tool, keeps control, and synthesises their results. Use it when you want one agent to own the workflow and talk to the user [S:2098057823930155319].
- **Decentralised pattern:** an agent hands off to a peer, which takes over execution together with the latest conversation state. It's a one-way transfer, ideal for triage, where a specialist should simply take over [S:2098057823930155319].

In Google's ADK workshop in the pack, Annie Wang builds the shared-board version: a root orchestrator first writes the evidence links into **session state**, which she describes as a shared whiteboard passed between agents and tools; then three specialist sub-agents run in parallel, read the board, and vote, with a two-out-of-three majority deciding [S:2106410521079538108].

### Decomposition: what you gain, what you lose

CMU's lecture on planning and multi-agent coordination lays out the trade-off honestly [S:2104635196910030894]:

- **Gains.** A subtask needs less context than the whole task (one sub-agent checks one vendor and doesn't need to think about the others). Different subtasks can use different models, including smaller, cheaper ones. In one experiment, putting a capable manager over cheap worker models raised performance a lot without a big rise in cost per task, because most actions were carried out by the workers.
- **Losses.** A decomposition is an abstraction that can miss details and be inflexible, and passing the *right* information between modules is hard. A single agent that manages its context well has every past action available.
- **Replanning matters.** On a long-horizon benchmark, an agent forced to stick to its first plan graph succeeded about a quarter of the time; allowing more rounds of replanning raised that steadily. As the lecturer puts it, plans should always be revisable.

The lecture ends with questions worth asking before you split: Are there clear subtasks? Are they separable? Would a dedicated model help with some of them? Is planning harder than doing? When should the system replan [S:2104635196910030894]?

### Fan out, fan in, and keep the glue in code

When subtasks really are independent, run them in parallel. Gyomei's guide recommends **bounded batches** (a concurrency cap so you don't hit rate limits all at once) and **fanning in only when the next step needs the full set** [S:2098057823930155319]. Filtering, counting, routing and de-duplicating results have fixed rules, so do them in plain code; save the model for the cross-item judgement, like ranking or finding one root cause behind several failures [S:2098057823930155319].

Claude Code's creator describes the cheapest fan-out of all: for a hairy problem, ask Claude to investigate three or five approaches in parallel with sub-agents, then pick the best and summarise [S:2106826633390772253]. The article quoted with that podcast warns against the opposite mistake: drawing a big graph before you've watched a capable agent actually do the work. Graphs pay off when there are real branches, parallel work, approvals or several specialists; for “one agent, three tools”, they can freeze assumptions too early [S:2106826633390772253].

### Width is the signal

A useful rule from the 24/7 “AI employee” guide: keep a cheap, always-on agent for routine work, and only call a large parallel team when a task is **genuinely wide** (it suggests a starting threshold of roughly 25 independent items), with a human approving the spend because team runs cost much more [S:2106410521079538108]. The vendor speed-up figures in that guide are the vendor's own; keep the principle, not the numbers.

> **Where the metaphor fails.** A colony's coordination was shaped by millions of years of selection and is robust to losing individual workers. Your topology was designed last Tuesday. Every extra agent adds another context window to pay for, another place for information to get lost in a handoff, and another failure point. Pheromone trails also evaporate on their own, which stops stale information from dominating. A shared state object doesn't evaporate unless you make it, so old or wrong entries keep steering every agent that reads it.

## 🛠 Lab: one manager, three summarisers, one honest comparison (15 min)

**Part A (3 min, phone OK).** For each job, write *single*, *manager* or *handoff*, and one reason: (1) summarise one paper; (2) summarise 30 papers into a comparison table; (3) route incoming lab emails to “data request”, “collaboration” or “admin” helpers that then reply themselves; (4) design a field season (sites, permits, budget, schedule) where each part depends on the others.

**Part B (12 min, at a computer).** Put **three papers you know well** into `~/learn-ai/labs/m14/papers/` as `.txt` files (title, abstract and methods pasted in is enough). Knowing them well is what lets you judge the summaries. Then, in Claude Code or Codex, paste:

```text
Work only inside ~/learn-ai/labs/m14. Use Python standard library only.
Write orchestrate.py, a manager-pattern orchestrator:
1. For each .txt file in papers/, start a worker with a headless call
   (`claude -p` if the claude command exists, else `codex exec`), at most 3 running at once,
   120-second timeout each. Worker prompt: "Summarise this paper as JSON with keys
   question, study_system, method, main_finding, one_limitation. Use only the text given.
   If a field is not in the text, write null." followed by the paper text.
2. Fan in IN CODE: parse each reply as JSON, reject and report any reply that isn't valid JSON or
   lacks a key (no model call for this step), and print a markdown comparison table.
3. Make ONE synthesis call with only the validated JSON objects: "In 5 sentences, what do these
   studies agree on, where do they differ, and what is the biggest open question?"
4. Write single.py: ONE headless call given all three papers at once, asking for the same table
   and the same 5-sentence synthesis.
5. Time both scripts and save outputs to results/.
Show me both scripts before running them. Then run both.
```

**What to check**

- Mark each table cell against your own knowledge of the papers: correct, vague, or wrong. Which version had more wrong or invented cells? Did any `null` appear where the paper genuinely lacks the information (good) or where it has it (a miss)?
- Compare wall-clock time and the number of model calls (5 versus 1). Was the manager version worth it for three papers? Ask your agent: *“At how many papers would the manager pattern clearly win, and why?”* Check its answer against today's reading on width and context.
- Did the code-based fan-in catch any malformed JSON? That's a step that needed no model at all.

Keep `orchestrate.py`: in m16 you'll give its workers roles, and the capstone's literature-triage team starts from it.

## 🧠 Self-check

**Q1. In the manager pattern and the decentralised pattern, what does an edge between two agents represent?**
A: In the manager pattern an edge is a tool call: the manager calls a worker and gets a result back, keeping control. In the decentralised pattern an edge is a handoff: control and the conversation state transfer one way to the peer, which takes over.

**Q2. OpenAI suggests splitting into several agents when there's “tool overload”. What actually causes the overload, and what should you try first?**
A: Overlap and similarity between tools more than their raw number. First try clearer tool names, parameters and descriptions; split into separate agents only if that doesn't fix the wrong tool choices.

**Q3. Give one gain and one loss of decomposing a task across agents, from the CMU lecture.**
A: Gain: each subtask needs less context, and cheaper or specialised models can handle some subtasks. Loss: the decomposition can miss details and is inflexible, and it's hard to pass exactly the right information between modules, whereas a single well-managed agent keeps all past actions available.

**Q4. In your orchestrator, why did the fan-in step use code rather than a model call?**
A: Parsing, validating keys, rejecting malformed replies and building a table have exactly one correct answer, so code does them with no cost, latency or variance. The model is saved for the cross-paper judgement in the synthesis step.

**Q5. How does the ant-colony picture mislead you about multi-agent systems?**
A: Colony coordination is evolved, robust and self-cleaning (trails evaporate). Agent topologies are designed and fragile: each added agent multiplies token cost and failure points, and shared state keeps stale or wrong entries unless you expire them.
