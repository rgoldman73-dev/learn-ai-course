## 🌿 The ecology hook

A young songbird isn't born knowing its song. It listens to a tutor, stores a template, practises a scrappy “subsong”, and refines it against the template until it matches. The result is a learned behaviour that can be passed on, varied, and, over generations, sorted into regional dialects by which versions get copied.

Agents now have something similar. A **skill** is a packaged, reusable behaviour: a folder with a `SKILL.md` file that says when to use it and how to do the job, plus optional scripts and reference files. You can write skills yourself (tutoring), and agents are beginning to write and rewrite their own (learning from practice). Today you'll do both, and see why a skill library that rewrites itself needs the same thing birdsong has: a template to check against.

## 📖 Concept: procedures that load on demand

### What a skill is

The Claude Code guide in the pack describes it simply: a folder inside `.claude/skills` with a `SKILL.md` file; the top block holds a **name** and a **description of when to use it**, and the instructions go below. Claude reads the description and activates the skill when it fits [S:2104402058963026288]. The Claude Code docs say when to make one: when you keep pasting the same instructions, checklist or multi-step procedure into chat, or when a section of `CLAUDE.md` has grown into a procedure rather than a fact [S:2098057823930155319].

Gyomei's CI example shows the shape: a `ci-triage` skill with a process, a “Never” list (don't disable the failing test, don't edit auth code, don't merge) and a fixed “Return” format. The scheduled loop then invokes the skill instead of carrying the procedure in its prompt [S:2098057823930155319]. Note the distinction Gyomei draws: **a skill adds a procedure to the current worker; it doesn't create a new worker or a separate context**. If you need isolation or restricted permissions, that's a subagent (m15) [S:2098057823930155319].

### Progressive disclosure: the description is always there, the body isn't

This is why skills scale. In a normal session only each skill's short **description** sits in context; the full body loads when the skill is invoked, so long reference material costs almost nothing until it's needed [S:2098057823930155319]. CMU's lecture on memory and skills walks through the same levels using the open-source Hermes agent: the system prompt lists available skills by their metadata, and a tool lets the model open the rest of a skill file when it decides to [S:2104635196910030894].

```text
 Level 1  always in context   name + description        "field-data-qc: check field CSVs for…"
 Level 2  on invocation       SKILL.md body             checklist, rules, output format
 Level 3  only if needed      supporting files/scripts  species_aliases.md, check_dates.py
```

A few details from the Claude Code docs that matter in practice [S:2098057823930155319]:

- `disable-model-invocation: true` stops Claude from triggering a skill on its own (use it for anything with side effects, like a deploy). `user-invocable: false` makes background-knowledge skills that only Claude loads.
- Once invoked, a skill's text **stays in the conversation** and isn't re-read, so write it as standing instructions. After compaction only a limited slice of recently used skills is carried forward, so very long skills can lose their tail.
- Every line of an invoked skill is a recurring token cost: state what to do, not why.

### Skills have become a standard

The harness source-code study found that `SKILL.md` skills are now the **most widely adopted extension standard**: 9 of 11 coding agents implement them (versus 8 of 11 for MCP, next module), and the format has converged on a folder with a `SKILL.md` whose YAML header requires at least a name and a description [S:2106479763636302271]. Eight of the nine load only the metadata up front and fetch bodies on demand, and some activate skills conditionally, for instance only when the agent touches matching files [S:2106479763636302271]. One agent even searches another vendor's skill folder, so skills written for Claude Code work there unchanged [S:2106479763636302271].

### Skills that agents write for themselves

Skills can be **written by people**, where you know where they came from and can control quality but they take time to write and maintain, or **induced** from the agent's own past experience, which is automatic but noisy [S:2104635196910030894]. The CMU lecture describes the research line:

- **Agent Workflow Memory** turns successful trajectories into reusable workflows. A judge model first predicts whether a trajectory was actually correct, because remembering incorrect workflows would steer the agent wrong later [S:2104635196910030894].
- **Programmatic skills** induce code functions instead of text. Code can be tested by executing it, which gives a stronger check, and a skill that works becomes a tool that cuts the number of steps on future tasks [S:2104635196910030894].
- **Limits.** A skill induced on one website broke on another whose page used radio buttons instead of a drop-down: skills may not generalise. And too many skills can distract a model; dropping rarely used ones can improve both efficiency and success [S:2104635196910030894].

In production, the harness study reports the first agent-authored skills: one agent has a background review agent that creates and patches skills from completed tasks, and another mines past sessions into skill patches that land in an inbox for human review [S:2106479763636302271]. In robotics, RPG has a robot practise in simulation, diagnose its failures and keep updating a shared skill library from them; its authors report high success after repeated rounds of self-improvement, in simulation and on real robots [S:2107871108338982988]. (That's the authors' own announcement; Unit 10 returns to it.)

### Test a skill like an intervention

The Claude Code docs make a point an experimentalist will like: seeing a skill trigger tells you Claude *found* it, not that it *helped*. Run a few realistic prompts in a fresh session **with and without** the skill and compare, because leftover context from writing the skill hides gaps in its instructions [S:2098057823930155319]. The skill-creator plugin automates this, including a blind A/B between two versions of a skill before you commit an edit [S:2098057823930155319].

> **Where the metaphor fails.** Song learning has selection built in: a bird's output is checked against a stored template, and across a population, versions that get copied spread while others die out. An agent rewriting its own skill library has **no template and no population** unless you add them. It can “improve” a skill into something worse and then load that worse version every time, a cultural drift with no selection. Worse, if the judge that decides what to keep is wrong, errors get stored and reinforced. The fixes are the ones the research uses: a check before anything is saved (a judge, a test, execution), a with/without comparison, and a held-out set the edits weren't tuned on.

## 🛠 Lab: a field-data-qc skill, tested like an intervention (15 min)

**Part A (3 min, phone OK).** List eight things that go wrong in field count spreadsheets you've handled (e.g. dates in three formats, “0” versus blank, species codes mixed with names, counts in the notes column). Star the two that cost you most. These go into the skill.

**Part B (12 min, at a computer).** In Claude Code, inside your capstone repo, paste:

```text
Work inside ~/learn-ai/capstone (keep its existing map files).
1. Create qc_data/ with three small messy field-count CSVs (15-25 rows each). Plant known problems:
   mixed date formats, a negative count, "12.0" counts, blank vs 0, species name variants and case,
   duplicate rows, a latitude out of range. Save the planted problems per file to
   qc_data/answer_key.json. Then create a 4th file, qc_heldout.csv, with different planted problems,
   and put its key in qc_heldout_key.json. Don't show me the held-out key yet.
2. Write the skill .claude/skills/field-data-qc/SKILL.md:
   name: field-data-qc; description: when to use it (checking field survey CSVs before analysis);
   body: a short checklist that includes [my two starred problems from Part A], the rule "a zero
   count is an observation, never drop it", "never modify the input file", and a fixed output:
   a JSON list of {row, column, problem, suggested_fix}. Put species-name variants in a supporting
   file species_aliases.md that the skill reads only when names look inconsistent.
3. Write eval_skill.py: for each of the 3 CSVs, run one headless call (`claude -p`) asking
   "Check <file> for data-quality problems; reply as a JSON list" from (a) this repo and (b) a copy
   of the repo in /tmp/noskill that has the same files but no .claude/skills folder. Score each
   reply against answer_key.json: problems found, problems missed, false alarms.
Show me SKILL.md and eval_skill.py before running. Then run the eval and print a table.
```

Then let the agent **rewrite its own skill**, and check it against the held-out file:

```text
Copy SKILL.md to ~/learn-ai/capstone/skill_versions/field-data-qc.v1.md. Based on the misses in the
eval, improve SKILL.md (v2). Re-run eval_skill.py with v2. Then run v1 and v2 once each on
qc_heldout.csv and score them against qc_heldout_key.json. Print one table: version, train recall,
train false alarms, held-out recall, held-out false alarms.
```

**What to check**

- With versus without the skill: did the skill actually help, or did the bare agent find most problems anyway? Either answer is useful.
- v1 versus v2: if v2 improved on the three training files but not on the held-out file, the rewrite was **tuning to the test**, the agent version of overfitting (you'll meet it again as Goodhart's law in Unit 8).
- Read v2's diff yourself. Did the agent add anything you disagree with as an ecologist (e.g. “drop rows with missing species”)? A self-rewriting skill needs a human or a test to stop that from becoming permanent.
- Codex users: Codex also reads `SKILL.md` skills; ask it where it discovers project skills in your version and put the folder there.

## 🧠 Self-check

**Q1. When should a procedure become a skill rather than a line in CLAUDE.md or a subagent?**
A: When you keep pasting the same instructions or multi-step procedure, or a CLAUDE.md section has grown into a procedure rather than a fact. Use a subagent instead when the work needs its own context or restricted permissions; a skill adds a procedure to the current worker without creating a new one.

**Q2. Explain progressive disclosure for skills in one or two sentences.**
A: Only each skill's name and description sit in context all the time; the full body loads when the skill is invoked, and supporting files load only if the body points to them. So a large library costs little until a skill is actually used.

**Q3. Why did Agent Workflow Memory use a judge before storing an induced workflow?**
A: Because storing workflows from incorrect trajectories would steer the agent wrong on future tasks. The judge predicts whether a trajectory succeeded so that only (probably) correct workflows enter memory.

**Q4. Your skill v2 beats v1 on the three files used to improve it but not on the held-out file. What happened?**
A: The edits were tuned to the training files (overfitting / teaching to the test). The held-out file is the honest measure; keep v1, or improve v2 using more varied examples and re-test on fresh held-out data.

**Q5. How does a self-rewriting skill library differ from song learning?**
A: Song learning checks output against a template and has population-level selection on which versions spread. A self-rewriting agent has neither unless you add them, so it can drift and store errors. You supply the selection with judges, tests, with/without comparisons and held-out sets.
