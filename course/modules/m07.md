## 🌿 The ecology hook

A genome on its own does nothing. It needs a body: sense organs to take in the environment, appendages to act on it, a metabolism that keeps the cycle running, an immune system that rejects what's dangerous, and some way to remember what happened. The same genome in a different body plan behaves very differently.

Unit 3 is about building that body. The trained model (the weights from Unit 1) is the genome. Everything wrapped around it, which lets it read files, run commands, remember, stop and stay safe, is the **harness**. The sources agree on a one-line formula: **agent = model + harness** [S:2106479763636302271], [S:2098057823930155319].

## 📖 Concept: the anatomy of a harness

### The model alone is tokens in, tokens out

The CMU agents course starts from the classic definition: an agent perceives its environment and acts on it. A coding agent's environment might be a repository or a website. It receives **observations** (your messages, file contents, tool results), takes **actions** (edit a file, run a command, reply) and, when you can define one, gets a **reward**, such as tests passing [S:2104635196910030894]. The language model itself only reads and writes tokens. The **harness** is what coordinates the tool calls, using the model as its engine [S:2104635196910030894].

OpenAI's practical guide names three core parts: a **model**, **tools**, and **instructions** [S:2098057823930155319]. LangChain's definition is the most useful for debugging: if it isn't the model, it's the harness. That covers system prompts, tools and their descriptions, the filesystem and sandbox, orchestration logic, and hooks [S:2098057823930155319].

### The core loop: metabolism

Every production harness runs the same basic cycle. The harness sends the model the task plus everything that has happened so far. The model replies with either a request to run a tool or a final message. If it's a tool request, the harness runs it, appends the result to the history, and calls the model again. This repeats until the model stops asking for tools [S:2106479644354474463]. OpenAI's guide lists the usual **exit conditions**: a final-output tool is called, the model answers without any tool call, an error, or a maximum number of turns [S:2098057823930155319]. In the research literature this reason-act-observe cycle is called **ReAct** [S:2104635196910030894].

```text
        ┌──────────── history (task + all past calls and results) ◄───────────┐
        ▼                                                                       │
   [ model ] ── "call read_file(x)" ──► [ harness runs the tool ] ── result ─────┘
        │
        └── no tool call / turn cap / error ──► STOP
```

### Seven subsystems

The harness source-code study (arXiv 2609.00006) took apart eleven production coding harnesses, including Claude Code, Codex CLI, Gemini CLI, OpenHands and the 100-line Mini-SWE-Agent. Every one of them takes a position on the same **seven subsystems**, and they differ only in size [S:2106479763636302271], [S:2106479644354474463]:

| Subsystem | Body part | Minimal form | Maximal form |
|---|---|---|---|
| **Agent loop** (stop conditions, recovery) | metabolism | a plain while loop over one bash tool | an event log that can replay a run |
| **LLM integration** (prompt, caching, routing) | nervous system | one API call, one template | many providers, model routing |
| **Tools & actions** | appendages | bash only | 43 typed tools, loaded on demand |
| **Memory & context** | memory | keep the whole history | notes the agent maintains across sessions |
| **Safety & permissions** | immune system | a step and cost limit | policy rules + reviewer model + OS sandbox |
| **Orchestration** (sub-agents) | division of labour | none (single agent by design) | sub-agents that spawn sub-agents |
| **Extensibility** (hooks, skills, MCP) | ? (no good analogy) | plain code | plugin marketplaces |

The study's examples: Mini-SWE-Agent is the floor, Claude Code has 43 typed tools with deferred loading, Codex combines policy rules with an LLM approval reviewer and an OS-level sandbox, and Aider skips sub-agents on purpose [S:2106479763636302271]. Skills (`SKILL.md`) appear in 9 of the 11 systems and MCP in 8 [S:2106479763636302271].

Two findings are worth remembering. First, **no production harness imports a general-purpose agent framework, and none retrieves code with vector embeddings**. They run on hand-rolled loops and plain search tools such as ripgrep [S:2106479763636302271]. Second, loop sophistication **doesn't predict benchmark performance**: the tiny Mini-SWE-Agent reports results in the same range as far larger systems. What size buys is production readiness: safety, recovery, cost control and extensibility [S:2106479763636302271].

### Harness or training?

The CMU lecturers point out that most agent capabilities (accurate tool calls, coherence over long context, safety) can be built *either* by training the model *or* by engineering the harness. The usual history is that a problem is patched in the harness first, and later trained into the next model [S:2104635196910030894]. LangChain observes the flip side: models are now post-trained inside particular harnesses, so a model can become oddly dependent on its home harness's tool formats [S:2098057823930155319].

### Diagnose by missing layer

The most practical use of the anatomy is debugging. Before you blame (or replace) the model, ask which layer is missing [S:2098057823930155319]:

| Symptom | Missing layer |
|---|---|
| It repeats yesterday's work | state / memory |
| It guesses your conventions | context (instructions, skills) |
| It can't reproduce the bug | tools or runtime access |
| A bad patch reaches review | verification |
| It does something unsafe | permissions |

A harness-design guide adds the one decision most people skip: **write the stopping rule in one sentence before you start**. “Done means the test suite passes and the app boots”, not “done means the agent says it's done” [S:2106479644354474463]. It also says the vendor owns the inner loop and built-in tools, but your instructions file, tests, permissions and definition of done are yours, whether or not you ever designed them [S:2106479644354474463].

> **Where the metaphor fails.** A body *develops from* its genome, so genome and body plan co-evolved and can't be pulled apart. A harness is engineered separately, by different people, and you can **swap it under the same model**. LangChain reports that one model scored far lower in its home harness than in others on a public benchmark, and that they moved their own agent from the top 30 to the top 5 by changing only the harness [S:2098057823930155319]. Imagine transplanting a genome into a new body and having it run faster. Also, no organism has a component whose job is to *forbid* actions in advance. Permissions are closer to a lab protocol than an immune system.

```text
Without changing any files or running any commands that modify anything, describe your own harness in this session.

1. Loop: how do you decide to take another step or stop? Is there a turn or time limit?
2. LLM layer: which model are you running as, and can it be changed mid-session?
3. Tools: list every tool you can call right now, one line each.
4. Memory & context: which instruction files were loaded at the start of this session, and what happens when the context fills up?
5. Safety: which actions need my approval, which are blocked, and is there a sandbox?
6. Orchestration: can you start sub-agents? How do they share context with you?
7. Extensions: which hooks, skills, plugins or MCP servers are active here?
For every claim, mark it [KNOWN] if it comes from your instructions or tool list, or [GUESS] if you are inferring.
```

Fill in the last column yourself: for your capstone, what does each subsystem need to do? (For example, Safety: “never write to data/raw/”.)

**What to check**

## 🧠 Self-check

**Q1. What does “agent = model + harness” mean in practice?**
A: The model only turns tokens into tokens. Everything else that makes it act (the loop, tool execution, prompt assembly, memory, permissions, sub-agents, extensions) is the harness. If a component isn't the model, it's part of the harness.

**Q2. Describe the core agent loop and two common exit conditions.**
A: Send the model the task plus history; if it requests a tool, run the tool, append the result and call the model again; repeat. Exit when the model replies without a tool call or calls a final-output tool, or when a turn cap, budget or error stops it.

**Q3. Name the seven harness subsystems from the source-code study.**
A: Agent loop, LLM integration, tools and actions, memory and context, safety and permissions, orchestration (sub-agents), and extensibility (hooks, skills, plugins, MCP).

**Q4. The study found a 100-line harness reporting benchmark results in the same range as million-line ones. What does the extra size buy?**
A: Production readiness rather than raw task success: safety and sandboxing, recovery from failures, cost control, extensibility and user experience.

**Q5. An agent's patches keep reaching your review with failing tests. Which layer do you fix first, and how?**
A: Verification: add a check that runs the tests and rejects the patch before it reaches you, and define done as “tests pass” rather than “the agent says it's done”.
