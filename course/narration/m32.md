# m32 narration: Stress-testing the ecosystem

Welcome to Module Thirty-Two, the last core module of the course.

You don't learn how stable a community is by watching it on a calm day. You disturb it. A pulse, like a flood or a removal. Or a press, like a steady supply of extra nutrients. Then you measure two things. Resistance: how little it changes. And resilience: how quickly it comes back.

Today you disturb your capstone on purpose.

Start with replication. Agents are not deterministic, so one successful run tells you very little. A source in the pack suggests running every task three times and judging the worst run. The arithmetic is sobering. If each attempt succeeds three times out of four, all three succeed less than half the time. And the typical failure isn't a crash. It's a fluent paragraph explaining why an error doesn't matter.

Then the disturbances. A data file with a missing column. Units swapped in one column. An empty file. An abstract with a hidden instruction telling your system to change its decision. A search index that isn't there. A model call that times out. For each one, you ask: did the system notice, and did it recover?

Then the budget. Every run costs tokens and time. A team at LangChain showed how to report this well. When they routed each task to the cheapest model that could handle it, they reported the typical cost, the average cost and the expensive tail, and right beside it, the quality measure, which didn't measurably change. They also tried always using the cheapest model. Their engineers complained within a day, and the test was stopped. Cheap is only a saving if it still works.

Finally, the decision. Anthropic's eval guide is clear: if a gain is within the noise, don't merge it. And one builder in the pack asks three questions of every component. Did adding agents find something one agent couldn't? Did the verifier catch something the worker missed? Was it worth what it cost? A component that fails all three gets cut, however clever it is.

Here's where the metaphor breaks. A forest recovers after a flood on its own. Your system has no recovery processes except the ones you build. Worse, it usually degrades silently, still producing tidy, confident output. So your evals have to keep running, every time a model, a prompt or your data changes.

In the lab, you'll set your budget first, before you see a single number. Then your coding agent builds one command that runs the whole eval suite and the disturbance tests, records cost and time for every call, groups the failures by cause, and writes a one-page report with ship, cut or fix for every component.

That report is the first page of your system's lab notebook. Start with Part A, and write down your budget now.
