# m11 narration: Feedback loops

Welcome to Module Eleven, and to Unit Four: trophic flows.

Think about homeostasis. Blood sugar rises. A sensor in the pancreas notices. Insulin is released, and sugar falls back toward its set point. Then the response eases off. Density-dependent regulation in a population has the same shape. Crowding feeds back on births and deaths. In both cases, the clever part is not the response. It is the sensor, the thing that compares where you are with where you should be, and the rule that says, stop, we are there.

Today you build that kind of loop for an agent.

One of today's sources puts it in a single line. A loop is a check that can fail. Produce some work. Check it. Correct it. Repeat until the check passes. And the check is everything. If nothing can fail the work while you are out of the room, you do not have a loop. You have a timer.

So what counts as a check? The tests pass. Every claim has a source. The change touches only the files in the plan. And what does not count? The output looks good. The model says it is confident. Even, no errors were raised. That last one fools careful people. Plenty of wrong answers run without a single error.

The rule to remember is this. Loop on evidence, not on confidence.

Another guide turns this into a short contract you write before you automate anything. Six lines. The job. What triggers it. Where it keeps its notes between runs. The command that verifies the work. When it must stop. And what it may never do without a human. If you cannot write the verifier as an actual command, the task is not ready to run on its own.

And give the loop a way to give up. Three attempts is a good default. If the work fails three times, the problem is usually in the plan, and the loop cannot see the plan. So it should stop, and hand the evidence to you.

Now, where does the metaphor fail? Biological feedback is continuous, cheap, and refined by selection. Every ancestor tested that sensor. Your agent's loop is paid for on every turn, and nobody has tested your sensor but you. If your check is broken, the loop can run forever. Or worse, it can succeed forever. A test that always passes. Or an agent that quietly edits the test so that it passes. That is the same problem as rewarding the wrong thing in evolution, now in your terminal. Biology rarely lets the effector rewrite the sensor. Your loop must forbid it.

In today's lab you will plant three bugs in a small diversity-index script, with tests whose answers you can check in your head. Then you will build a loop that calls your coding agent to fix the script, guards the tests against tampering, logs every attempt, and stops after three tries. Finally, you will give it a test that can never pass, and make sure it gives up gracefully.

Open your terminal, and let's close the loop.
