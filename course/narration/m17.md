# m17 narration: Appendages

Welcome to Module Seventeen, and to a new unit: niches, and the tools that let an agent fill one.

Show an ornithologist a beak, and they'll tell you what the bird eats. A stout cone cracks seeds. A long curved bill probes flowers. A hooked tip tears flesh. Form fits function, and that fit is what makes an organism good at its niche.

An agent's appendages are its tools. On its own, a model can only produce text. Tools let it look things up, calculate exactly, read your files and change things in the world.

Why does a model need them? The CMU course gives two reasons. Some things a model simply cannot do. Its knowledge was frozen when training ended, so it can't know today's date, or what's in your database, without asking something. Other things it can do, but badly or slowly. It can multiply two big numbers by reasoning step by step, but a calculator is faster and never wrong.

Here's the key idea for today. Unlike a beak, a tool is made of words and rules. It has a name, a description, and a schema. The schema says exactly what a valid call looks like. Which fields are required. What type each one is. Which values are allowed. Metres and hectares, yes. Acres, not in this tool.

And now the clever part. A schema can be turned into a grammar, and the grammar can police the model while it writes. At each step, before a token is drawn, every token that would break the rules gets its probability set to zero. You've seen this move before, in the module on temperature. It's the same sampling step, with a filter in front of it. This is called constrained decoding, and it means the model's tool calls almost always come out well formed.

But notice the word formed. Constrained decoding guarantees grammar, not meaning. A perfectly valid call can still ask for the wrong species, or the wrong file.

So the rest of the job is design. Keep tools few and clearly different, because two tools with similar names cause more mistakes than one missing tool. Make errors that teach, saying which field was wrong and what is allowed. And limit what each tool can reach.

Here's where the beak metaphor breaks. A beak is fixed for life, and its fit was tested by selection over generations. Tools can be added in seconds, and nothing tests them except you. A finch never picks the wrong beak because the label was ambiguous. A model chooses tools by reading their descriptions. And every tool you add costs space in the context window, on every turn, whether it's used or not.

In the lab, you'll build three tools for your capstone: a taxonomy lookup, a file reader that can only see one folder, and a unit converter. Then you'll give a model ten requests, some tricky, one dangerous, and watch which tool it reaches for.

Let's go and grow some appendages.
