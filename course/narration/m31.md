# m31 narration: Assembling the ecosystem

Welcome to Module Thirty-One.

Community assembly is one of ecology's oldest puzzles. A set of species arrives at a site. Some are filtered out. Some coexist because they use different resources. Some interactions hold the whole community together. And order matters. The first arrivals change what can follow.

Today you assemble your own community. A router that decides how hard each job is. Two specialist agents, one triaging new papers against your notebook, one checking your field data. A memory to search. Verifiers that try to break every claim. And you, approving the final step. All of these parts already exist, built across this course. Today they become one system.

The ecological rules translate well. First, niche differentiation. Each agent owns its own work, and no two agents ever write the same file. One source in the pack puts it neatly: if a job recurs every week, give it an agent. If it happens once, it's a skill.

Second, interactions must be explicit. A handoff between agents is a file at a known place, with a fixed shape. It says who sent it, who receives it, and what done looks like for the next stage. And every role says what to do when the payload is incomplete, because an agent that's helpful without the facts is writing fiction.

Third, structure. A course in the pack has a sentence worth memorising. The loop lives inside a node. The graph lives between nodes. Inside each specialist, produce, check, correct, and repeat until the check passes, at most three times. Between specialists, split the work, merge it with plain code, and send through a gate. If one piece fails, send back only that piece, with the reason and a strict scope. Send back the whole batch, and correct work gets rewritten and the run never settles.

Fourth, order of arrival. Build the checks before the workers. Write each check so a program can run it, and feed it a known bad record to prove it can fail.

Here's where the metaphor breaks. Real communities assemble themselves, and unplanned interactions can still find a balance. Your system only has the interactions you build. An untested connection doesn't settle down. It fails quietly.

In the lab, your coding agent will assemble the pipeline from your earlier builds, without rewriting what already works. Contracts first, then checks, then roles, then the pipeline, then a map of the whole system and four small state files. Then a dry run on five abstracts and twenty rows of real field data. Finally, three tests. Did the output appear without you watching? Could a stranger understand it? Does a second run look the same?

Start with Part A. Write a four-line card for each of your two specialists, and one sentence that says when a run is done.
