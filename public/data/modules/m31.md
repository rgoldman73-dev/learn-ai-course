## 🌿 The ecology hook

Community assembly asks how a set of species arriving at a site turns into a functioning community: who gets in (filtering), who coexists (niche differentiation), and which interactions hold the whole thing together. Order matters too: priority effects mean the first arrivals shape what can follow.

Today you assemble your capstone community: the harness and router, two specialist agents, a memory, the verifiers, and one human approval at the end. The ecological rules translate surprisingly well. Each specialist needs a distinct niche (no two agents writing the same file), interactions must be explicit (handoffs as files with fixed shapes), and assembly order matters (contracts and checks first, specialists second).

### Assembly rules from the pack

**1. The loop lives inside a node; the graph lives between nodes.** Hanako's "Loops and Graphs" course puts it in one sentence. Inside a unit of work: produce, check, correct, repeat until green. Between units: split, fan out, merge, gate, send back [S:2091515787366306154]. Its vocabulary has only four node types: **splitter, worker, code node, gate**, and the code node is the one people forget: merging, ranking and deduplicating have exactly one correct answer and belong in code, not in a model [S:2091515787366306154].

**2. Write the check first, so a program can evaluate it.** "The test suite exits 0" or "every claim carries a source line" is a check; "the output looks good" and "no errors were raised" are not [S:2091515787366306154].

**3. Return the unit, not the batch.** When one slice fails, send only that slice back, with its verdict, reason, evidence and a **scope line** ("fix this file only"); otherwise correct work gets rewritten and the run stops converging. Cap corrections at three; a unit that fails three times has a problem in the plan [S:2091515787366306154].

**4. One owner per artefact, and handoffs are files.** Lummox's agent playbook says to hire agents "by what they own": if a job recurs every week it's an agent; if it happens once it's a skill. When two agents would write the same file, cut one [S:2105607355262009622]. A handoff has a sender, a receiver, a payload path and a definition of done for the next stage; each role file says what it owns, what it receives and emits (from whom, at which path), what it never does, and what it does when the payload is incomplete. That last item matters: "helpful without a payload is fiction" [S:2105607355262009622].

**5. Fences for the verbs that matter.** The same playbook lists five verbs an agent may not finish without approval: **send, spend, publish, delete, legal**, enforced by the runtime rather than written as prose the model may "interpret" [S:2105607355262009622]. For your capstone, "publish" and "delete" (overwriting raw field data) are the ones to fence.

**6. Put the human at one point.** Open the gate by blast radius, not by the model's confidence; put the human at the step of highest consequence and lowest reversibility, and nowhere in the middle, where "a human in the middle of a graph becomes the slowest node in it" [S:2091515787366306154].

### The map: one instructions file and four files on disk

The harness-design article summarised alongside the Wavestone paper gives the files that let a system survive crashes and fresh sessions: **SPEC.md** (what you're building; the agent never edits it), **PLAN.md** (steps with plain acceptance criteria), **PROGRESS.md** (done, next, tried and failed), **DECISIONS.md** (append-only, every choice and why), plus a commit after every change that works. Its slogan: if it isn't in a file, it doesn't exist [S:2106479644354474463]. Its "weekend version" starts with one instructions file under a hundred lines that works as a table of contents into a docs folder, and a stopping rule written in one sentence before you start [S:2106479644354474463]. That's your m05 map, now covering the whole system.

### Judge the run by the folder

Lummox's three tests for whether an agent is really doing a job, not chatting about it [S:2105607355262009622]:

- **The lid test:** you left, and the output folder still appeared.
- **The stranger test:** someone who isn't you can open the folder and know what happened.
- **The repeat test:** the next run's folder has the same structure, with new facts.

> **Where the metaphor fails.** A natural community assembles itself: species arrive, interact in ways nobody specified, and the stable configurations persist. Your system has only the interactions you build and test. There's no emergent mutualism between your triage and QA agents unless you write the handoff; there's no competitive exclusion when two agents fight over a file, just silent overwrites. And untested interactions don't settle into equilibrium: they fail quietly. Assembly here is engineering, so every edge needs a contract and every node needs a check.

**Part A (3 min, phone OK).** For each of your two specialists (triage and QA, or whatever your m30 spec named), write a four-line card: **name, owns, definition of done, fence** [S:2105607355262009622]. Then write the one-sentence stopping rule for a whole run.

**Part B (12 min, at a computer).** Paste into Claude Code or Codex:

```text
Work in ~/learn-ai/capstone. Read CLAUDE.md, CAPSTONE_SPEC.md and docs/ first. Reuse my earlier builds (some already
in ~/learn-ai/capstone, e.g. harness/ and fieldqa/; others in ~/learn-ai/labs) by importing them or copying
them into components/ with a note of the source; do not rewrite working code. Build in this order and show me each step before moving on:
1. contracts/: JSON schemas for every handoff (router decision, triage record, QA flag, verifier verdict,
   run summary). Each handoff is a file with sender, receiver, payload path, definition of done.
2. checks/: the GREEN conditions as code (schema validation, every claim cites a source chunk,
   flags reference a real row and rule). Write a test that feeds one known-bad record and must FAIL.
3. roles/: one role file per specialist with: owns, receives (from, path), emits (to, path),
   never does, what to do if the payload is incomplete. Use my cards: [paste Part A].
4. pipeline.py: router -> splitter -> triage and QA workers (each with a produce-check-correct loop,
   max 3 attempts, failed units returned alone with verdict/reason/evidence/scope) -> code node merge
   -> gate (components/checkers.py) -> runs/<date>/ with brief.md, triage.csv, flags.csv, log.jsonl.
   Fence: never modify files under data/raw/; never publish or send anything.
5. SPEC.md (copy of CAPSTONE_SPEC.md, read-only by convention), PLAN.md, PROGRESS.md, DECISIONS.md;
   update CLAUDE.md (under 100 lines) as the map of the whole system. Commit after each working step.
6. Dry run on a small slice: 5 abstracts from my notebook and 20 rows of one real field CSV in data/raw/.
Then run the lid, stranger and repeat tests: run it twice and diff the two run folders' structure.
```

**What to check in the result**

- Did the known-bad record fail the checks? If not, fix the checks before anything else.
- Open `runs/<date>/` cold, as a stranger would. Can you tell what happened, what was flagged and why, and what needs your approval?
- Run twice: same folder structure, same fields? (The repeat test.)
- Look in `log.jsonl` for any unit that hit three attempts. What does it say about your plan or your rules?
- Is `data/raw/` untouched? Check the timestamps.

## 🧠 Self-check

**Q1. What are the seven parts every harness shares, according to the Wavestone study?**
A: Loop, LLM layer, tools, memory, safety, orchestration and extensions (hooks, skills, MCP). Harnesses differ in the size of each part, not in having them.

**Q2. "The loop lives inside a node; the graph lives between them." What goes in each?**
A: Inside a node: produce, check, correct, repeat until the check passes (with a cap). Between nodes: splitting, fanning out, merging (in code), gating and sending failed units back.

**Q3. One of four parallel slices fails its check. What should go back, and with what?**
A: Only the failing slice, with its verdict, the reason, the evidence and a scope line limiting the fix to that slice. Sending the whole batch back rewrites correct work, adds new uncertainty and can stop the run converging.

**Q4. What makes a handoff between agents robust?**
A: It's a file at a known path with a fixed shape (schema), a named sender and receiver, a definition of done for the next stage, and a stated behaviour for incomplete payloads, rather than intent reconstructed from a chat.

**Q5. Why is "community assembly" an imperfect analogy for building this system?**
A: Natural communities assemble themselves and unspecified interactions can still stabilise. Your system only has the interactions you build; untested edges fail silently (for example two agents overwriting one file), so every edge needs a contract and every node a check.
