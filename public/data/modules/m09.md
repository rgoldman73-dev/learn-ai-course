## 🌿 The ecology hook

Ethologists distinguish **fixed action patterns** from **flexible behaviour**. A fixed pattern runs the same sequence every time it's triggered (the greylag goose rolling a stray egg back to its nest is the textbook case): cheap, fast, reliable in the environment it evolved for, and absurd outside it. Flexible foraging adjusts to each patch: costlier, slower to decide, but able to cope with the unexpected. Most animals use both, matched to the problem.

Yesterday you built an agent that chooses its own steps. Today's question: when should you let it choose at all? Often the better answer is a fixed sequence of model calls that *you* designed, called a **workflow**.

## 📖 Concept: the simplest pattern that works

### Two kinds of agentic system

Anthropic's “Building effective agents” draws the line that most of the field now uses [S:2098057823930155319]:

- **Workflows**: models and tools orchestrated through **predefined code paths**. You write the sequence.
- **Agents**: the model **dynamically directs its own process and tool use**. It writes the sequence.

The same post gives the rule this whole module rests on: find the simplest solution possible and only add complexity when it's needed. That might mean not building an agentic system at all, because agentic systems trade latency and cost for better task performance [S:2098057823930155319]. OpenAI's practical guide agrees: before building an agent, check that the task really involves complex judgement, rules too tangled to maintain, or heavy unstructured data. Otherwise a deterministic solution may be enough [S:2098057823930155319].

### The pattern catalogue

Anthropic describes five workflow patterns, in rising order of autonomy [S:2098057823930155319]:

| Pattern | Shape | Use it when | Ecology echo |
|---|---|---|---|
| **Prompt chaining** | step 1 → (gate) → step 2 → … | the task splits cleanly into fixed steps; trade latency for accuracy | a fixed action pattern |
| **Routing** | classify, then send to a specialised path | distinct categories that are better handled separately | habitat selection |
| **Parallelisation**: *sectioning* or *voting* | independent pieces at once, or the same task several times | speed, or more confidence from multiple attempts | many foragers, one patch |
| **Orchestrator-workers** | a central model splits the task on the fly and delegates | subtasks can't be predicted in advance | a colony allocating workers |
| **Evaluator-optimizer** | one model drafts, another critiques, loop | clear criteria, and feedback measurably helps | trial-and-error learning |

Then come **agents**: models using tools based on feedback from the environment, in a loop, for open-ended problems where you can't predict the number of steps or hard-code a path. They cost more and errors can compound, so the post recommends testing them in sandboxes with guardrails [S:2098057823930155319]. The CMU lecturers put the trade-off in system terms: declarative workflow tools (orchestrators) are more guardrailed but less expressive, while coding-agent harnesses give a single agent a huge action space [S:2104635196910030894].

Evidence that fixed pipelines can hold their own comes from the harness source-code study. It cites **Agentless**, a fixed localise-repair-validate pipeline reported to be competitive with agent loops on a standard coding benchmark, as a useful counterweight to the assumption that more autonomy is always better [S:2106479763636302271].

### How practitioners actually mix them

In a long interview, Claude Code's creators describe it as something to **compose like a Unix utility**. Headless mode (`-p`) suits read-only, well-defined jobs inside a larger workflow, such as generating a changelog from the commit history. Interactive sessions are for open-ended work [S:2106826633390772253]. For hairy problems Boris asks Claude to investigate the same question three or more times in parallel and pick the best answer [S:2106826633390772253]. That's parallelisation by voting, inside an agent.

An article quoted in the same post offers a diagnostic table for when to add structure. If the first attempt is close but unreliable, wrap it in a loop with an external check. If several specialists must run in a fixed order, make the graph explicit. If the workflow keeps changing, keep control model-driven and don't freeze it into a diagram yet [S:2106826633390772253].

```text
Is the sequence of steps known in advance?
 ├─ yes → can each step be checked? ── yes → PROMPT CHAIN with gates
 │                                    └─ no  → chain + EVALUATOR step
 └─ no  → are subtasks independent once known? ── yes → ORCHESTRATOR-WORKERS
                                                 └─ no  → single AGENT with tools, caps and a verifier
```

> **Where the metaphor fails.** A goose didn't choose its egg-rolling routine; selection fixed it over many generations, and the goose pays nothing extra each time it runs it. You choose per task, today, and the bill is paid **on every run**. A flexible agent spends tokens deciding what a workflow already knows, and it can decide differently each time (m02). Also, animals can't inspect their own repertoire. You can read a workflow's code and test each step, which is a large part of why workflows are easier to trust.

## 🛠 Lab: one triage task, two repertoires (15 min)

A literature-triage task, done twice: once as a fixed **prompt chain** and once as a **free agent** that plans its own steps. This uses about 10 headless calls.

**Step 1 (3 min). Make the test set.** Start Claude Code or Codex in `~/learn-ai/capstone` and paste:

```text
Create data/triage/ with:
- criteria.md: inclusion rule = "field studies that measure an effect of water temperature on freshwater invertebrates".
- abstracts.jsonl: 20 short invented abstracts (60-100 words each), fields id and text. Make 8 clearly include,
  8 clearly exclude (lab-only, marine, vertebrates, modelling-only...) and 4 borderline.
- labels.csv: id,label (include/exclude) — your intended answer for each, with borderline ones marked in a note column.
Show me labels.csv. Do not show the abstracts to any later model call together with the labels.
```

Skim five abstracts against `labels.csv` and fix any label you disagree with. You're the ground truth.

**Step 2 (7 min). Build both repertoires.** Paste:

```text
Create labs/triage_compare.py (Python standard library only) in this repo that runs two approaches on data/triage
and never shows labels.csv to the model:
A) CHAIN (fixed workflow): for batches of 5 abstracts, call 1 = extract JSON per abstract
   {id, organism_group, habitat, setting: field|lab|model, measures_temperature: yes|no};
   a CODE gate checks every id is present and fields are valid (retry the batch once if not);
   call 2 = apply criteria.md to the extracted JSON and return {id, decision, reason}.
B) AGENT (free): ONE headless call run inside data/triage that says "Triage abstracts.jsonl using criteria.md.
   Decide your own approach. Print only CSV lines id,decision,reason."
Use `claude -p` if available, otherwise `codex exec`, read-only, 180-second timeout per call.
Record for each approach: number of model calls, total wall-clock seconds, and — if the CLI offers a JSON output
mode that reports cost or tokens (check its --help) — total cost/tokens.
Score both against labels.csv: accuracy, and list every disagreement. Save results to labs/triage_results.md.
Show me the script, run it, then print triage_results.md.
```

**Step 3 (5 min). Read the disagreements.** For each approach, look at the cases it got wrong. Were they borderline items? Was the chain's error in extraction (call 1) or in the decision (call 2)? Could you even tell where the free agent went wrong?

**What to check**

- Which was cheaper and faster? Which was more accurate? (With 20 items, a difference of one or two isn't meaningful. Note it anyway.)
- The chain's intermediate JSON lets you point to the exact step that failed. That **inspectability** is often the decisive advantage of workflows.
- Run the free agent a second time. Did its decisions or its approach change? (m02: sampling varies.)
- Write a one-line verdict in your notes: “For literature triage in my capstone I'll use ___ because ___.”

## 🧠 Self-check

**Q1. What distinguishes a workflow from an agent in Anthropic's definition?**
A: In a workflow, models and tools run through predefined code paths that you wrote. In an agent, the model dynamically decides its own steps and tool use.

**Q2. Name the five workflow patterns and one situation suited to each.**
A: Prompt chaining (fixed steps, such as outline then check then write); routing (distinct categories, such as easy vs hard queries); parallelisation (independent sections, or voting for confidence); orchestrator-workers (unpredictable subtasks, such as multi-file code changes); evaluator-optimizer (clear criteria where critique helps, such as polishing a translation).

**Q3. Why might a fixed pipeline beat an autonomous agent on a well-defined task?**
A: It's cheaper and faster (no tokens spent deciding what to do next), more consistent run to run, and each step can be inspected and checked. Evidence like the Agentless pipeline shows fixed pipelines can be competitive even on coding benchmarks.

**Q4. When do you actually need an agent?**
A: When the task is open-ended, you can't predict the number or kind of steps, and you can't hard-code the path, and when you can sandbox it, cap it and verify its output.

**Q5. How does the fixed-action-pattern analogy break?**
A: Selection fixed animal routines over generations and running them costs nothing extra. You choose the pattern per task, and flexibility is paid for in tokens and unpredictability on every run. Unlike an animal, you can also inspect and test a workflow's steps.
