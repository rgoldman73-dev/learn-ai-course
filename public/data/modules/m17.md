## 🌿 The ecology hook

Show an ornithologist a beak and they can tell you a lot about the diet: a stout cone cracks seeds, a long decurved bill probes flowers, a hooked tip tears flesh. Form fits function, and the fit is what makes an organism good at its niche.

An agent's appendages are its **tools**. A model on its own can only produce text; tools let it look things up, compute exactly, read files and change the world. But unlike a beak, a tool is defined in words and numbers: a name, a description and a **schema** saying exactly what shape a valid call must have. Today is about designing those appendages so they fit the job, and so they're hard to misuse.

## 📖 Concept: what a tool really is

### Why give a model tools at all

CMU's tool-use lecture sorts tools into two kinds. Some do what the model **fundamentally can't**: its parameters are frozen at training time, so it can't know today's date or a database's current contents without calling something. Others **facilitate** what it can do slowly or unreliably: a model can multiply two seven-digit numbers by reasoning, but a calculator is faster and exact [S:2104635196910030894]. Typical tools look up fresh evidence, compute exactly, access private state (your files, your account), or act on the outside world [S:2104635196910030894].

OpenAI's guide groups tools by what they do to the workflow: **data** tools retrieve context (query a database, read a PDF, search the web), **action** tools change things (send a message, update a record), and **orchestration** tools are other agents used as tools, as in m14's manager pattern [S:2098057823930155319].

### The definition is a contract

A tool definition is structured data sent along with the prompt: a name (say `get_weather`), a description, and parameters with types, for example a required `city` of type string [S:2104635196910030894]. The model is trained to emit calls in a particular format, and that format differs between model families, so a harness can't assume one model's syntax works for another [S:2104635196910030894].

The lecture lists what a valid call must satisfy [S:2104635196910030894]:

1. **Syntax**: it parses as JSON. A single missing closing bracket throws an exception.
2. **Shape**: required fields are present.
3. **Types**: `city` is a string, `count` is an integer.
4. **Values**: allowed values only, e.g. units must be Celsius or Fahrenheit.

All four can be written in **JSON Schema**, which gives you machine-readable validation rules [S:2104635196910030894].

### Constrained decoding: making invalid calls impossible

Here's the clever part, from the same lecture. A JSON schema can be turned into a **grammar**. Regular expressions can't describe nested JSON, but a context-free grammar can, and a pushdown automaton (a state machine with a stack) can check it one token at a time [S:2104635196910030894]. At every generation step, the inference engine asks the grammar which next tokens would keep the output valid, sets every invalid token's score to minus infinity, and renormalises so that probability falls only on valid tokens [S:2104635196910030894].

```text
 schema says next must be:  "units": ("celsius" | "fahrenheit")      (illustrative numbers)
 model's raw next-token probabilities after the grammar mask
   "celsius"      0.41                  "celsius"      0.75
   "fahrenheit"   0.14                  "fahrenheit"   0.25
   "kelvin"       0.30      ──mask──▶   "kelvin"       0     (−∞)
   "}"            0.15                  "}"            0     (−∞)
```

You've seen this move before: it's m02's sampling step, with a rule-based filter applied before the draw. With it switched on and a correct schema, you almost always get well-formed calls [S:2104635196910030894]. Two important limits:

- **Running out of tokens.** If generation hits the output-length limit, you can be on a valid path but not at the end: half a JSON object [S:2104635196910030894].
- **Form, not meaning.** Constrained decoding guarantees the call *parses*; it doesn't guarantee it's *right*. A grammatical call can still ask for the wrong city [S:2104635196910030894].

Different providers implement their own decoding engines, which is one reason the same model can behave differently on different services [S:2104635196910030894].

### Code as a tool, and why it's a power tool

Instead of calling tools one at a time, a model can write a short program that calls them in loops. The lecture cites results where this raised success rates and cut the number of interaction turns, even on tasks that weren't obviously about code. But code is high-powered: it can loop forever, pull in a compromised library, and is harder to constrain and validate [S:2104635196910030894]. (The coding agents you use are built around exactly this power tool, which is why m13's permissions matter.)

### Designing tools that are hard to misuse

From the pack's harness-design guide and OpenAI's guide:

- **The menu is the world.** The model can't see your systems; it sees a menu of tool descriptions, and that menu is all it knows [S:2106479644354474463].
- **Fewer, distinct tools.** Two tools with confusingly similar names cost more than a missing tool; remove tools you never see used [S:2106479644354474463]. Overlap, not count, is what causes wrong choices [S:2098057823930155319].
- **Errors that teach.** “Invalid request” tells the model nothing, so it guesses. Return which field was wrong, what a valid value looks like, and what to try next [S:2106479644354474463].
- **Don't load every tool up front.** Each connected tool description sits in context on every turn [S:2106479644354474463]. The harness source-code study found the bigger agents now **defer** most tools: only a core set is in the prompt, and the model searches for the rest by keyword when it needs them (Codex uses a BM25 index over tool descriptions, the same algorithm you'll meet in m20) [S:2106479763636302271].
- **Rate the risk.** Rate each tool low, medium or high by read-only versus write access, reversibility and financial impact, and pause or escalate before high-risk calls [S:2098057823930155319].

The same study found tool sets range from a single shell tool to over a hundred built-in tools across the eleven agents it examined [S:2106479763636302271]. There's no single right size; there's a right fit for the niche.

> **Where the metaphor fails.** A beak is fixed for life and its fit was tested by selection over generations. Tools can be bolted on or removed per task in seconds, and nothing tests their fit except you. A finch also never chooses the wrong beak because its description was ambiguous; a model picks tools by **reading** their descriptions, so a vague description is a maladaptive trait that appears instantly. And every extra appendage has a running cost: its description crowds the context window on every turn, whether or not it's used.

## 🛠 Lab: three appendages and a choice test (15 min)

**Part A (3 min, phone OK).** Write, in plain words, a schema for `convert_units`: what fields, which are required, and which unit values you'd allow. Then list two requests a field ecologist might make that your schema should *reject* (e.g. converting hectares to kilograms).

**Part B (12 min, at a computer).** In Claude Code or Codex, paste:

```text
Work only inside ~/learn-ai/capstone/tools (create it). Python standard library only.
1. Write tools.py with three tools, each with a JSON-Schema-style definition (name, description,
   parameters with types, required fields, enums) and a Python implementation:
   - lookup_taxon(name: string): offline stub that looks the name up in a small dict of 5 marine
     species and returns {accepted_name, status}; unknown names return a structured not-found error.
   - read_file(path: string): may read ONLY files inside ./data/; anything else returns an error.
   - convert_units(value: number, from_unit, to_unit): enums limited to m, cm, km, m2, ha, km2;
     length<->area conversions are an error.
2. Write validate(call, schema): checks syntax, required fields, types and enums, and returns
   structured errors {field, problem, allowed_values, hint}. No third-party libraries.
3. Write choose.py: for each of the 10 requests below, make one headless call
   (`claude -p` if available, else `codex exec`) that gives the model the three tool definitions and
   the request, and asks for ONLY a JSON object {"tool": ..., "arguments": {...}} or {"tool": null}
   if no tool fits. Validate the reply, run the tool if valid, and log request, chosen tool,
   valid yes/no, error, result to choices.csv.
Requests:
 a) What's the accepted name for Lutra canadensis?   b) Convert 2.5 ha to m2.
 c) Read data/sites.txt (create this file with 3 site names).   d) Read ~/.ssh/id_rsa.
 e) Convert 12 acres to ha.   f) How far is 3 km in cm?   g) Convert 5 m to m2.
 h) What's the capital of Peru?   i) Is Enhydra lutris a valid name?   j) Show me sites.txt.
Show me tools.py before running anything.
```

**What to check**

- In `choices.csv`, count: right tool chosen, valid calls, and rejected calls. Requests d, e and g should be **rejected by your code**, not by the model's good manners. Which ones did the model refuse itself, and which did your validator catch?
- Request h should get `{"tool": null}`. Did the model invent a tool call anyway?
- Request j is ambiguous (which folder?). Look at what happened. Then rewrite **one** tool description to be clearer, re-run, and note whether choices changed. Tool descriptions are prompts.
- Ask your agent: *“If our model provider used constrained decoding with these schemas, which of our failures would disappear and which would remain?”* A good answer: malformed JSON and invalid enum values disappear; wrong-tool choices and semantically wrong arguments remain.

## 🧠 Self-check

**Q1. Give one tool a model fundamentally needs and one that merely helps, with reasons.**
A: Needs: anything fresher than its training data or private to you (today's date, a database query, your files), because its parameters are frozen. Helps: a calculator or code execution, because the model can reason through arithmetic but slowly and less reliably.

**Q2. What four properties must a valid tool call satisfy, and what can express all of them?**
A: Syntax (parses as JSON), shape (required fields present), types (each field has the right type) and allowed values (e.g. units in an enum). JSON Schema expresses all four.

**Q3. How does constrained decoding guarantee well-formed output, and what can still go wrong?**
A: The schema becomes a grammar; at each step the engine masks every token that would make the output invalid (score set to minus infinity) and renormalises over valid tokens. It can still fail if generation runs out of tokens mid-object, and it never guarantees the call is semantically right.

**Q4. Name three design choices that make a tool hard to misuse.**
A: Any three of: narrow scope (read only inside `data/`), enums and required fields, distinct non-overlapping names and descriptions, structured error messages that say what's wrong and what's allowed, risk ratings with pauses before high-risk calls, and deferring rarely used tools instead of loading all of them.

**Q5. Why is “tools are like beaks” misleading?**
A: Beaks are fixed and their fit was tested by selection; tools are added or removed per task with no testing unless you do it. Models choose tools by reading descriptions, so ambiguous wording causes wrong choices, and every tool description costs context on every turn.
