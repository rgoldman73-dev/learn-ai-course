## 🌿 The ecology hook

If you've ever scored animal behaviour from video, you know the routine. Before anyone's scores count, two observers score the same clips independently, you compute their agreement, and you retrain whoever drifts. Without that **inter-observer reliability** check, a change in "aggression" might just be a change in who was watching.

Yesterday's eval used a code grader: exact match on a label, which can't drift. But many outputs (a summary, an answer from your field notebook, a literature synthesis) have many valid forms. For those you need an observer, and increasingly that observer is another language model: an **LLM judge**. Today is about calibrating that observer, measuring a retrieval system with the right metrics, and recording **traces** so you can see *where* a failure happened.

## 📖 Concept: who grades, what to measure, where to look

### Code grader first, judge only when you must

Anthropic's eval guide says to use the cheapest grader that fits. If outputs are constrained, use code: exact match, a label from a fixed set, a schema check, tests that pass. Use an **LLM-as-judge** only when the output is open-ended but has clear quality criteria [S:2104676099083190435]. When you do use a judge, the guide sets four rules [S:2104676099083190435]:

- The judge reads the input, the output and a **rubric written as checkable claims**, not a 1-to-5 scale, and returns a score with its reasoning.
- For comparisons with a baseline, it sees both outputs **in random order, without being told which is the baseline**, and picks the better one.
- The judge **should not be the model you are testing**.
- Before trusting it, grade a handful of cases and ask yourself whether you'd have scored any differently, and run the judge **twice on the same output** to see whether its verdict changes.

The awesome-evals list summarises what goes wrong with judges, citing practitioner and research work: **position bias** (preferring whichever answer comes first), **verbosity bias** (preferring longer answers) and **self-preference** (models recognising and favouring their own text) [S:2105008692655743208]. The list's annotations also repeat two operational rules from Hamel Husain and Shreya Shankar's evals FAQ: prefer **binary** (pass/fail) judgments over Likert scales, and read a lot of traces yourself [S:2105008692655743208]. Tools now exist to measure a judge against held-out human labels with agreement statistics such as Cohen's kappa, and to test it for length, position and self-preference bias [S:2105008692655743208].

> **Background (not from the pack):** Cohen's kappa is the agreement statistic you may know from behavioural ecology: observed agreement corrected for the agreement two raters would reach by chance. Kappa near 0 means chance-level agreement even if raw agreement looks high (for example when 90% of items are "pass").

### Four metrics that split a RAG failure in two

A retrieval-augmented system (your m20-m22 builds) can fail in two places: it can **retrieve** the wrong evidence, or it can **generate** an answer the evidence doesn't support. The AI-engineer roadmap in the pack is blunt about which is more common: most RAG failures are retrieval failures, not model failures [S:2033587293064204349]. Ragas and DeepEval, two open-source evaluation libraries, provide metrics that separate the halves [S:2106462125874987099] [S:2105607355262009622]. DeepEval's README defines them like this [S:2105607355262009622]:

| Metric | Question it answers | Half it tests |
|---|---|---|
| **Contextual recall** | Does the retrieved context contain what the expected answer needs? | retrieval |
| **Contextual precision** | Are the relevant chunks ranked above the irrelevant ones? | retrieval |
| **Faithfulness** | Does the output factually agree with the retrieved context? | generation |
| **Answer relevancy** | Does the output actually address the question? | generation |

Read them as a diagnostic key:

```text
                     faithfulness HIGH            faithfulness LOW
recall HIGH    ✔ working                       generator invents or ignores evidence
                                               → fix the prompt / model
recall LOW     answer is "faithful" to the     both halves broken
               wrong evidence (or says "I     → fix retrieval first
               don't know") → fix retrieval
```

Most of these metrics are themselves LLM judges under the hood. DeepEval says its metrics can be powered by any LLM you choose, by statistical methods, or by NLP models that run locally [S:2105607355262009622], and Ragas likewise mixes LLM-based and traditional metrics [S:2106462125874987099]. Everything above about calibrating judges applies to them too.

The roadmap's practice project for this stage is exactly what you'll do in the lab: write question-answer pairs from your own documents, score answers for faithfulness and relevance, then change one thing (chunk size, model, top-k) and re-run [S:2033587293064204349].

### Traces: debug the path, not the guess

A trace is a structured record of one run: the input, every model and tool call, the retrieved chunks, intermediate outputs, tokens, latency and cost. The roadmap explains why ordinary monitoring isn't enough: a model can return a "200 OK" and still produce a useless or hallucinated answer, so you trace every call (prompt, output, tokens, latency, cost) [S:2033587293064204349]. The awesome-agent-observability list puts it in one line: for agents, "wrong" is a quality judgement rather than a status code [S:2105008692655743208].

Two open-source tools in the pack do this at scale. **Langfuse** traces LLM calls plus retrieval, embedding and agent actions, can be self-hosted (Docker Compose on your own machine), and supports LLM-as-judge, code evaluators, user feedback and manual labelling on those traces [S:2105607355262009622]. **DeepEval** can attach evaluations to traced steps so you score the whole trajectory, not just the final answer [S:2105607355262009622]. Lummox's architecture line puts them in context: model → context → planner → memory → tools → execution → **eval** → retry, with tracing and evals under "keep it alive" [S:2105607355262009622].

You don't need a platform today. A JSON file per run, written by your own code, is a perfectly good trace, and it's what you'll build.

> **Where the metaphor fails.** Two human observers can be trained against each other until they agree, and their errors are mostly independent. An LLM judge is a relative of the system it grades: it was trained on similar data, shares similar blind spots, and may prefer text that looks like its own. High agreement between a judge and the generator can mean both are right, or both are wrong in the same way. So you calibrate the judge against **your** labels, not against another model, and you keep a code grader wherever one is possible.

## 🛠 Lab: score your retrieval pipeline with a calibrated judge (15 min)

You'll use the search you built in m21 (hybrid BM25 + embeddings over this pack). If that folder is missing, the prompt falls back to plain BM25 via `learn-ai-rag/corpus/query.py`, which works the same way for this exercise.

**Part A (4 min, phone OK).** Open your m20 notes, where you wrote ten questions about the pack and labelled top-5 hits. For each question, write a one-sentence **expected answer** in your own words (what a correct answer must contain). These are your ground truth.

**Part B (11 min, at a computer).** This makes about 60 short headless calls. Paste into Claude Code or Codex (add your ten questions and answers):

```text
Create ~/learn-ai/labs/m24 and work only inside it, in a Python venv (.venv). Don't touch other folders.
1. Retriever: reuse my hybrid search from ~/learn-ai/labs/m21 if it exists (import it, don't edit it);
   otherwise call learn-ai-rag/corpus/query.py with --json and k=5. Show me which one you used.
2. qa.jsonl: my 10 questions (from ~/learn-ai/labs/m20/questions.txt) with my expected answers (below).
3. rag.py: for each question, retrieve top-5 chunks, then GENERATE an answer with `claude -p`
   using only those chunks (say "I don't know" if they don't contain the answer).
4. Judge: use a DIFFERENT model family from the generator if available (`codex exec` if installed;
   otherwise `claude -p --model <a different model>` in a fresh call). The judge never sees which
   system produced the answer.
5. Metrics, each as pass/fail with a one-line reason, judged per question:
   contextual recall (chunks contain what the expected answer needs),
   contextual precision (relevant chunks ranked above irrelevant),
   faithfulness (every claim in the answer is supported by the chunks),
   answer relevancy (answers the question).
   Try DeepEval first (pip install deepeval, wrap the judge CLI as a custom model).
   If DeepEval's custom-model setup takes more than 5 minutes to get working, implement
   these four metrics yourself with the definitions above and tell me you did.
6. Traces: write traces/<qid>.json with the question, retrieved chunk ids and scores, the exact
   generator prompt, the answer, each metric verdict and reason, wall-clock latency per call.
7. Judge checks: (a) re-run the faithfulness judge on all 10 answers and report how many
   verdicts changed; (b) print the 10 answers and chunks in judge_check.md so I can mark
   faithful yes/no myself, then compute raw agreement and Cohen's kappa with the judge.
8. report.md: a table of the 4 metrics per question, totals, and the 2x2 diagnosis
   (recall vs faithfulness) for each failing question.
My questions and expected answers: [paste]
```

**What to check in the result**

- Did you fill in `judge_check.md` yourself *before* looking at the judge's verdicts? Then look at kappa. If agreement is poor, the judge's scores for this task aren't trustworthy yet: tighten the rubric into checkable claims and re-check.
- How many faithfulness verdicts flipped on the second run? Any flips mean grader noise you'd otherwise mistake for system changes.
- Open five traces, starting with the worst. For each, decide: retrieval failure or generation failure? Does that match the 2x2 in `report.md`?
- Change one thing (k from 5 to 10, or BM25-only versus hybrid) and re-run. Which metric moved?

## 🧠 Self-check

**Q1. When should you use an LLM judge rather than a code grader?**
A: Only when outputs are open-ended (many valid answers) but there are clear quality criteria. If outputs are constrained (a label, a schema, tests), a code grader is cheaper, deterministic and can't share the system's biases.

**Q2. List three practices that make an LLM judge more trustworthy.**
A: Any three of: a rubric written as checkable claims rather than a 1-5 scale; binary verdicts; a judge model different from the one being tested; blind, randomly ordered pairwise comparisons; running the judge twice on the same output to check stability; comparing its verdicts with your own labels (agreement or kappa) before trusting it.

**Q3. Your RAG answers score high on faithfulness but low on contextual recall. What's wrong, and where do you fix it?**
A: The generator is faithfully summarising the evidence it got, but the retriever isn't fetching what the answer needs. Fix retrieval (more candidates, hybrid search, better chunking, query rewriting), not the generation prompt.

**Q4. Why isn't "no errors in the logs" a good sign that an agent run went well?**
A: Because the failure that matters is usually a quality failure, not a crash: the call returns successfully with a wrong or hallucinated answer. You need traces that record inputs, retrieved context and outputs so you can check the content, plus evals that score it.

**Q5. Give one way the inter-observer analogy breaks for LLM judges.**
A: Human observers can be trained against each other and their errors are fairly independent. An LLM judge shares training data and blind spots with the generator and can prefer text like its own, so judge-generator agreement can mean both are wrong in the same way. Calibrate against your own labels.
