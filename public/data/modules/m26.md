## 🌿 The ecology hook

Domestic strains are rarely the most impressive members of their lineage. A bantam is smaller than a junglefowl, a lab strain of *Arabidopsis* would lose in the wild, a dwarf wheat gives up height. What you gain is a strain that fits *your* conditions: your bench, your greenhouse, your budget, under your control.

Running a language model on your own computer is the same bargain. You give up the biggest, smartest models. In return you get a model that lives on your hardware, never sends your data anywhere, never changes without your say-so, and costs nothing per extra call. Unit 9 is about artificial selection; today you bring a strain home, and in the next two modules you start breeding it.

## 📖 Concept: what fits, what runs fast, what's good enough

### What you're buying, and what you're not

Movez's ten-step local-LLM course lists four things a local model gives you that an API can't: your data never leaves the machine, nobody can change your limits, an extra request costs nothing, and the model stays the same until you replace it [S:2106761689123139973]. It is just as clear about what you *don't* get: the smartest model on the market. On the intelligence index it quotes, a 27-billion-parameter open model that fits on a desktop GPU scores 34, the best open model 46 and the best closed model 58 [S:2106761689123139973]. And local isn't automatically cheaper: one analysis it cites priced a high-end desktop at more per million output tokens than the same open model through a cloud API. The course's summary: you go local for **control and unmetered volume**, not to beat the price list [S:2106761689123139973].

### Memory decides what loads; bandwidth decides how fast

A local model is a file (the weights) plus a program that runs it [S:2106761689123139973]. Two hardware facts follow from how generation works. To produce each token, the program reads every *active* weight from memory once. So **memory size** decides which models load at all, and **memory bandwidth** sets the ceiling on tokens per second; raw compute comes third [S:2106761689123139973]. A simple rule from the same course: the download should be no bigger than about two thirds of your memory. On an Apple Silicon Mac the whole memory is available; on a Windows or Linux PC the model wants the graphics card's own memory (VRAM), with ordinary RAM as a slow fallback [S:2106761689123139973].

One distinction saves confusion. A **dense** model uses all its weights for every token. A **mixture-of-experts** model stores many weights but activates only a fraction per token. Total parameters set the memory you need; active parameters set the speed [S:2106761689123139973].

### Quantisation: fewer bits per weight

Weights ship as 16-bit numbers. **Quantisation** stores them with fewer bits so the file shrinks. Movez's example: a 27B model is 55 GB at full precision and about 17 GB at 4 bits; the common "Q4_K_M" format is the default because benchmarks showed no measurable loss at a third of the size [S:2106761689123139973]. Go lower only when the model won't fit, and expect **agentic tasks to degrade before trivia does** [S:2106761689123139973].

That warning is worth an example. A heavily compressed ("ternary") version of the same 27B model is advertised at 98.2% of the original's aggregate score, but on a long-horizon agent benchmark the same vendor data show 52.8 against 69.7 [S:2106761689123139973]. An average across many benchmarks can hide a large drop on the one task you care about. That's why you test on your own eval.

### The other half of memory: the context cache

The weights are only half the bill. The model also keeps a cache for every token in the context window (the KV cache). Movez's budget formula is: **total = model file + context cache + 1-2 GB of runtime headroom** [S:2106761689123139973]. For their 27B example at 4 bits, an 8K context adds about half a gigabyte, while the full 262K window adds over 16 GB and no longer fits on a 24 GB card [S:2106761689123139973].

```text
 memory budget (one GPU or unified memory)
 ┌──────────────────────────────┬──────────────┬──────┐
 │ weights (shrink: quantise)   │ KV cache     │ 1-2GB│
 │                              │ (grows with  │ head-│
 │                              │  context -c) │ room │
 └──────────────────────────────┴──────────────┴──────┘
 tokens/sec ≈ limited by how fast memory can be read (bandwidth)
```

A practical trap: Ollama's default context window is only a few thousand tokens, so a local chat "forgets" after a few pages unless you start the server with a larger window (for example `OLLAMA_CONTEXT_LENGTH=16384`), which you then pay for in memory [S:2106761689123139973].

### Learn what the wrapper hides

Sudo su's advice to beginners is to learn llama.cpp, the engine underneath Ollama and LM Studio, because the friendly apps hide exactly the parts you're supposed to learn [S:2104017679908540472]. The settings they list map straight onto the diagram above: `-c` (context size, and what each extra token costs in VRAM), `-ngl` (how many layers sit on the GPU, and why speed falls off a cliff when they don't all fit), `-ctk`/`-ctv` (quantising the KV cache), `-np` (parallel slots, each costing memory), `--jinja` (the chat template: the difference between tool calls that work and ones that don't), and reasoning effort (a thinking model left on maximum can spend its whole budget thinking and return an empty answer) [S:2104017679908540472]. Their method is the one you'll use: **change one flag at a time and measure tokens per second every time** [S:2104017679908540472].

In their longer guide, the same author shows what this looks like across consumer GPUs from 8 to 24 GB, and is careful about it: every number comes from one card at a time, measured on the llama.cpp build of that day, and there's a cliff where speed collapses once the context outgrows the card [S:2106704758048485654]. Their 6 GB result is a useful reality check: only part of the model fits on the GPU and it crawls, "fine for a chat and no good for an agent" [S:2106704758048485654].

### Measure two speeds, then measure quality

Ollama's `--verbose` flag prints two rates: **prefill** (how fast the model reads your prompt) and **decode** (how fast it writes) [S:2106761689123139973]. They fail differently: decode is how fast the answer streams, while prefill is what makes long documents feel slow, especially on Apple Silicon, and most apps only show you decode. Movez's rough scale: 20 tokens per second is usable, 50 comfortable [S:2106761689123139973]. Then test **quality** on your own work: keep a file of tasks you already know the answers to and run it against every model and quantisation you consider [S:2106761689123139973]. You built exactly that file in m23.

### Where small local models earn their keep

Most calls inside an agent are not hard: pick a tool, pull three fields out of a page, decide whether a message needs a human. Movez cites an NVIDIA Research argument that such repetitive, scoped calls belong to small models, with 40% to 70% of an agent's model calls movable to a small model in their case studies, and shows a router that sends classify/extract/yes-no work to a 4B local model at temperature 0 [S:2106761689123139973]. That's the role your local model will play in the capstone: the cheap "reflex" layer from m10.

> **Where the metaphor fails.** Domestication is adaptation: generations of selection fit a strain to your conditions. Quantisation is not adaptation, it's **lossy compression**: the same model with less precise weights, slightly worse everywhere and sometimes much worse on long, multi-step tasks. A smaller model isn't tuned to your habitat either; it's a smaller generalist. Fitting it to your tasks takes actual selection: fine-tuning on your own labelled examples, which is tomorrow's module.

## 🛠 Lab: bring a strain home and measure it (15 min)

**Part A (3 min, phone OK).** Look up your computer's memory: total RAM, chip (Apple Silicon or not) and, on a PC, the graphics card's VRAM. Using the two-thirds rule, write down the largest model download that should fit [S:2106761689123139973].

**Part B (12 min, at a computer).** Ollama is free. The agent will install it, but **you** approve the install command when it asks. Paste into Claude Code or Codex:

```text
Work in ~/learn-ai/labs/m26. Ask me before installing anything system-wide, and never use sudo without asking.
1. Check whether `ollama` is installed; if not, show me the official one-line installer from ollama.com
   for my OS and wait for my OK. Then pull qwen3:4b (about 2.6 GB). If my machine has under 8 GB of
   memory, suggest a smaller model from the Ollama library instead and explain why.
2. Write bench.py (standard library + subprocess only). Each trial runs
   `ollama run <model> --verbose "<prompt>"`, parses prompt eval rate (prefill tok/s) and eval rate
   (decode tok/s), then runs `ollama ps` to record memory and the CPU/GPU split.
   Append one row per trial to bench.csv: model, context_length, prompt_tokens, prefill_tps, decode_tps,
   memory, processor, notes. Run each setting 3 times and keep all rows.
3. Change ONE setting at a time, restarting `ollama serve` when needed:
   a) short prompt (one sentence) vs long prompt (paste ~1,500 words from learn-ai-rag/CATALOG.md);
   b) OLLAMA_CONTEXT_LENGTH = 4096, 16384, 32768 (same short prompt).
4. Quality: if ~/learn-ai/labs/m23/test.jsonl exists, classify those 10 items with the local model through
   the OpenAI-compatible endpoint http://localhost:11434/v1 at temperature 0, using my m23 prompt.md,
   and report accuracy next to my m23 result. Otherwise make 10 labelled items with me first.
5. Write results.md: a table of medians per setting, which setting moved which number, and a
   one-paragraph verdict: for which of my tasks is this local model good enough?
```

**What to check in the result**

- Does `ollama ps` say the model runs fully on the GPU (or on Apple Silicon)? If it's split with the CPU, expect decode speed to drop sharply [S:2106761689123139973].
- Long prompt versus short: which rate changed, prefill or decode? Raising the context length: did memory go up even though the prompt didn't change?
- Compare local versus m23 accuracy on the same ten items. Is the gap within the noise you learned to estimate in m23?
- Note your decode speed against the 20/50 tokens-per-second scale. Is it fast enough to sit inside an agent loop?

## 🧠 Self-check

**Q1. What decides which models you can load, and what decides how fast they generate?**
A: Memory size decides what loads (weights plus context cache plus headroom must fit). Memory bandwidth sets the ceiling on tokens per second, because every active weight is read from memory once per generated token.

**Q2. Your 4-bit model fits easily, but when you raise the context window to the full length it runs out of memory. Why?**
A: The context (KV) cache grows with the context window, and it's a separate memory cost on top of the weights. At long contexts it can be many gigabytes. Use a smaller window, quantise the KV cache, or use a smaller model file.

**Q3. A compressed model is advertised at "98% of the original". Why should you still test it on your own eval?**
A: An average over many benchmarks can hide a big drop on a particular kind of task. In the pack's example the same compressed model scored far lower on a long-horizon agent benchmark. Agentic, multi-step tasks tend to degrade before trivia does.

**Q4. What's the difference between prefill and decode speed, and which one makes long documents feel slow?**
A: Prefill is how fast the model reads your prompt; decode is how fast it writes the answer. Long inputs are dominated by prefill, which many apps don't show you.

**Q5. Why is "quantisation is like domestication" misleading?**
A: Domestication adapts a strain to your conditions through selection. Quantisation is lossy compression of the same generalist model: nothing is adapted to your tasks. Adapting it requires fine-tuning on your own examples.
