## 🌿 The ecology hook

A food chain is a line: grass, grasshopper, shrew, owl. Real communities are **webs**. Several consumers draw on the same resource at once, flows split and merge between compartments, and each compartment's output becomes someone else's input. When you draw a web you're forced to say exactly which compartments are connected, and by what.

Yesterday's loop made *one* unit of work reliable. Today you'll draw the web around many units: what runs, what runs at the same time, what waits, where results merge, and where they get checked. That's **graph engineering**.

## 📖 Concept: nodes, edges, and the arrows that aren't real

### Nodes and edges

The Loops and Graphs course defines the two parts in one breath. A **node** is a unit of work: one bounded job, one input in, one output out. An **edge** is a dependency: this node's output feeds that node's input [S:2091515787366306154]. The most common mistake is treating “and then” as an edge. “Summarise the file and then check the weather” has no edge: the weather check never reads the summary. The test for every arrow: **can you name the variable that crosses it?** If not, the wait is pure waste [S:2091515787366306154].

Ryven's “Graph Engineering” essay found the same fake waits in his own workflows. He redrew a forty-step chain, cut about a dozen arrows that carried nothing, and the run then finished at the speed of the slowest *real* dependency chain, with no model change at all [S:2104873702198538738]. A plain line of steps is already a graph, just the weakest one: one stalled step blocks everything after it [S:2104873702198538738].

### Give every node a contract

A node becomes usable when its output has a fixed shape, enforced by a schema instead of hoping the model returns something parseable [S:2104873702198538738]. Gyomei's guide shows a node contract (inputs, one job, a typed output such as `classification: env | flake | bug | dependency | infra`) and then makes the **edge a plain function**: read one validated field, return the next node. One input should always produce the same route. And the default branch should point to a human, so an unexpected value stops the automated path [S:2098057823930155319].

### Four kinds of node, and one isn't a model

The Loops and Graphs vocabulary is small [S:2091515787366306154]:

| Node | Job | Note |
|---|---|---|
| **Splitter** | cuts the work into units | decides more than any other node; splitting along the wrong dimension wastes everything downstream |
| **Worker** | does one unit, with one lens, in **its own context** | workers sharing one context window converge on the first finding: you pay four times for one opinion |
| **Code node** | merge, rank, deduplicate, compare | if you can describe it without “judge, decide, assess, summarise”, it's code, not a model call |
| **Gate** | lets work through or sends it back | build it first |

Ryven's recurring pattern is **fan out, reduce, synthesise**: independent workers in parallel, a reduce step in plain code (flatten, deduplicate, filter: “deterministic, instant, free”), then one final synthesis [S:2104873702198538738]. Gyomei adds the practical limits. Fan out in **bounded batches** with a concurrency cap, so one failed worker doesn't erase its neighbours' results. Fan in to a model only when the next step needs to compare across the whole set [S:2098057823930155319]. Two traps from Ryven: parallel workers writing to the same files overwrite each other (give each its own git worktree), and pouring a thousand raw results into one synthesis step degrades quietly once the context overflows (summarise in batches, then synthesise the summaries) [S:2104873702198538738].

### Don't let the generator grade itself

Ryven's most important lesson came after his fan-out “looked done”: each worker had checked its own output. He cites research that models can recognise and prefer their own writing, including one study in which judges favoured their own answers with noticeably higher win rates [S:2104873702198538738]. His fix: a separate verifier node on the edge, whose only job is to try to kill the finding, **with a completely fresh context**. A verifier that sees the worker's reasoning just nods along [S:2104873702198538738]. Even then, verifiers that all check against the same underlying source agree with each other without verifying anything. You need **anchors**: a test that actually ran, a number that actually landed, a frozen rule [S:2104873702198538738].

### The way back

A graph without a return path is a pipeline that never learns. The Loops and Graphs course names two return paths [S:2091515787366306154]:

- **Correction edge (short):** a gate sends **one unit** back to the node that produced it, never the whole batch, because re-doing correct work makes it different, not better. The return carries a unit, a verdict, a reason, the evidence and a **scope** (“fix this file only”). Cap it at three attempts.
- **Learning edge (long):** an accepted result becomes a **constraint** in the splitter's brief, so every later run starts where this one ended. It's the one almost everybody skips.

The course's gating rule: open the gate on **blast radius**, not confidence. Reversible, contained work can flow; hard-to-reverse work (deletions, migrations, anything touching raw data) gets a lane that never opens automatically [S:2091515787366306154].

### How much does parallelism buy?

Ryven applies **Amdahl's law**: speed-up S = 1 / ((1 − p) + p/N), where p is the fraction of the work that is genuinely independent and N is the number of parallel agents. With p = 0.95 and N = 16 you get about 9×, not 16×. With p = 0.70, under 3× [S:2104873702198538738]. The fake-edge test is how you estimate p before spending anything.

### When not to draw a graph

Graphs pay off when there are real branches, parallel work, approvals or recovery paths. They can also **freeze assumptions too early**: if the model must invent the plan as it goes, forcing every path into a diagram makes the system more brittle, not less [S:2106826633390772253]. Ryven skips graphs for small fixes, for exploratory work, and whenever the fake-edge test finds no real independence: then it's a loop, and a loop is exactly right [S:2104873702198538738].

```text
records ─► [SPLITTER: code] ─► batch 1 ─► [WORKER] ─┐
                            ├─► batch 2 ─► [WORKER] ─┼─► [MERGE: code] ─► [GATE: rules + fresh verifier] ─► report
                            └─► batch n ─► [WORKER] ─┘          ▲                   │
                                                                └── correction: one batch, with scope
          learning edge: accepted rule ─► splitter brief (rules/brief.md) for next run
```

> **Where the metaphor fails.** Energy flows one way down a food chain and is lost at every step. In an agent graph, **information flows backwards on purpose**: correction edges return a unit to its producer, and learning edges rewrite how the next run is split. Nothing in a food web edits the web itself. And a food web is discovered, not designed. A graph you design can lock in your first wrong guess about how the work divides, which is why the sources say to formalise only the paths you've seen work.

## 🛠 Lab: a field-data QA graph in plain Python (15 min)

**Step 1 (4 min). Data with known faults.** In `~/learn-ai/capstone`, paste into Claude Code or Codex:

```text
Create data/field/records.csv: 30 invented stream-invertebrate survey records with columns
id, date, site, lat, lon, taxon, count, observer. Plant exactly these faults and list them in
data/field/planted_faults.csv (id, fault): 3 negative or non-integer counts, 2 impossible dates,
2 misspelled taxa, 2 coordinates far outside the study area (pick a bounding box and state it in docs/data.md),
and 1 exact duplicate record. Everything else must be clean. Do not show planted_faults.csv to any later model call.
```

**Step 2 (8 min). Build the graph.** Paste:

```text
Create graph/qa_graph.py (Python standard library only) implementing this graph, and print a timeline of node start/end times:
1. SPLITTER (code): read records.csv, split into 6 batches of 5; read rules/brief.md (create it empty if missing) as extra instructions.
2. WORKERS (model, parallel, max 3 at once, each a fresh headless call: claude -p or codex exec, 180 s timeout, read-only):
   each gets one batch plus the study-area box and returns JSON only:
   [{"id":..., "issues":[...], "severity":"ok"|"minor"|"major"}] for every id in the batch.
3. MERGE (code): validate the schema; every id exactly once; flag exact duplicate rows with plain code.
   If a batch fails validation, send ONLY that batch back to its worker once, with UNIT, VERDICT, REASON, EVIDENCE
   and SCOPE ("return JSON for these 5 ids only").
4. GATE: (a) deterministic rules in code (negative/non-integer counts, impossible dates, coordinates outside the box);
   (b) ONE fresh-context verifier call that sees only the records marked major plus the raw rows (never the workers'
   reasoning) and must answer keep or drop for each, with a reason.
5. REPORT (code): graph/qa_report.md with each flagged record and which nodes flagged it, then score against
   data/field/planted_faults.csv: found, missed, false alarms, per node (workers, rules, verifier).
Also print an Amdahl estimate: p = (total worker seconds) / (total run seconds summed over all nodes), N = 3.
Show me the code, run it, and show qa_report.md.
```

**Step 3 (3 min). Add a learning edge.** Look at the misses. Write one constraint you learned into `rules/brief.md`, for example *“Taxon names must match the list in docs/data.md exactly. Flag near-misses as major.”* Re-run the graph and compare found/missed. Commit as “qa graph v1”.

**What to check**

- Which node caught what? Deterministic rules should catch the count, date and coordinate faults every time. If a model was needed for those, move them into code.
- Did the duplicate get caught by the code node? It should never need a model.
- Did the fresh verifier drop any false alarms from the workers? Did it wrongly drop a real fault?
- Look at the timeline. Did the workers actually overlap? Compare the Amdahl estimate with the real speed-up.
- Did the learning edge change the next run? That's the return path most systems never build.

## 🧠 Self-check

**Q1. How do you tell a real edge from a fake one?**
A: Ask whether the next step actually reads the previous step's output: can you name the variable that crosses the arrow? If not, the two steps are independent and can run in parallel. The wait came only from the order you wrote them in.

**Q2. Name the four kinds of node and say which one should never be a model call.**
A: Splitter, worker, code node and gate. The code node (merge, rank, deduplicate, compare) should be plain code, because those operations have one correct answer and a model only adds cost, latency and variance.

**Q3. Why must a verifier have a fresh context, and why isn't that enough on its own?**
A: A verifier that sees the worker's reasoning tends to accept it, and models also tend to prefer their own outputs. A fresh context breaks that priming. But verifiers that all rely on the same source can agree without verifying anything, so you still need anchors: tests that ran, deterministic checks, frozen rules.

**Q4. What's the difference between a correction edge and a learning edge?**
A: A correction edge sends one failed unit back to its producer, with evidence and a narrow scope, to fix the current run. A learning edge turns an accepted result into a constraint in the splitter's brief, so every future run improves.

**Q5. 80% of your workflow is independent work and you run 8 workers. What speed-up should you expect at best?**
A: Amdahl's law: 1 / (0.2 + 0.8/8) = 1 / 0.3 ≈ 3.3×, not 8×. The serial parts (split, merge, gate) cap the gain.
