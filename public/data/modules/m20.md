## 🌿 The ecology hook

A forager in a patchy landscape faces one question over and over: stay or go? Charnov's **marginal value theorem** gives the answer: leave a patch when your rate of gain there drops to the average rate you could get across the whole habitat, counting travel time. Rich patches deserve longer visits; depleted ones should be abandoned early.

An agent answering a question from documents is a forager too. The documents are cut into **chunks** (the patches), a search engine ranks them, and the agent works down the list. Every chunk it reads costs context and attention; the first few hits are usually the richest; at some point another chunk adds less than it costs. This unit is about **retrieval-augmented generation (RAG)**: fetching the right evidence before answering. Today you'll learn the classic keyword ranker, **BM25**, and use this course's own source pack as your first RAG system.

## 📖 Concept: rare words, repeated words, long passages

### Keyword search first

The production agentic-RAG course in the pack deliberately starts with keyword search before adding vectors, and gives its reasons: keywords excel at exact technical terms, IDs and precise phrases; you can see exactly why a result was retrieved; and it's fast and needs no embedding model [S:2105259648001376474]. In week 3 it builds BM25 search over arXiv papers with **field boosting** (a match in the title counts three times, in the abstract twice, in the body once) [S:2105259648001376474].

The harness source-code study found something striking in the coding agents you use every day: across roughly four million lines of code, **none of the eleven agents retrieves code with vector embeddings**. They use deterministic tools such as text search, syntax parsing, file globs and auto-discovered Markdown context files [S:2106479763636302271]. For code and for technical text full of exact names, keyword search is often enough.

### How BM25 scores a chunk

> **Background (the standard BM25 formula, as implemented in this pack's `corpus/query.py`):** for each query word that appears in a chunk, BM25 adds
> `idf × tf × (k1 + 1) / (tf + k1 × (1 − b + b × length / average_length))`
> and sums over the query words.

Three ideas hide in that line:

1. **Rarity (idf).** A word found in few chunks is informative; a word found everywhere isn't. “Compaction” narrows the field; “agent” barely does. Very common words are also dropped entirely as stop words.
2. **Repetition with diminishing returns (tf and k1).** A chunk that mentions your word five times is more likely about it than one that mentions it once, but not five times more. `k1` sets how fast the gain saturates: low `k1` means one mention is almost as good as many.
3. **Length normalisation (b).** Long chunks contain more words by chance, so they're penalised. `b = 0` switches the penalty off; `b = 1` applies it fully.

The pack's `query.py` also indexes each chunk's title twice, a simple form of the field boosting above. Try it all in the widget:

### Chunking: how big is a patch?

Documents are too big to retrieve whole, so they're cut into chunks first. Ronin's roadmap names the core trade-off: chunks that are **too large lose retrieval precision**, chunks that are **too small lose context** [S:2033587293064204349]. It describes three families (fixed-size, recursive, semantic), suggests fixed-size chunks with overlap as the baseline, and gives one starting point of about 250 tokens with 10 to 20% overlap so information at the boundaries isn't lost [S:2033587293064204349]. The production course instead chunks **by document section** where structure exists, targeting about 600 words with 100-word overlaps and a 100-word minimum [S:2105259648001376474]. This pack's corpus uses chunks of a similar size (median about 577 words), so a whole idea usually fits in one patch.

Ronin's list of retrieval failures is a good diagnostic checklist [S:2033587293064204349]:

- **Chunk boundary:** the answer is split across two chunks. Fix: more overlap or structure-aware chunking.
- **Top-k too small:** the right chunk exists but ranks sixth. Fix: retrieve more, then narrow down.
- **Missing metadata:** the chunk matches but comes from the wrong document, date or author. Fix: store metadata and filter on it (like `query.py`'s `--topic` and `--source`).
- And the headline: most RAG failures are retrieval failures, not model failures.

### When to leave the patch

Jeff Dean sketches where this is heading: retrieval over enormous collections, then lightweight models that judge how relevant, say, 30,000 retrieved documents are, and finally only the hundred or so that matter most go into the model's context window [S:2106489085829488811]. That's a staged forager: a cheap, fast first pass across many patches, then expensive attention spent only on the best. Your `-k` value is the simplest version of the decision: how far down the list is it worth reading?

You need a number to decide. **Precision@5** is the fraction of the top five hits that are actually relevant to the question; averaged over a set of questions, it tells you whether a change to the search made things better or worse.

> **Where the metaphor fails.** A forager learns patch quality from experience and updates its leaving rule. BM25 learns nothing: the same query gets the same ranking forever, however often the top hit disappoints you. It doesn't know what words *mean*, so a synonym or a paraphrase is invisible to it (“carrying capacity” won't find “context window limit”). And the marginal value of a chunk isn't fixed by the ranking; it depends on what the agent has already read, because a second chunk saying the same thing adds nothing. Tomorrow's embeddings fix the first gap, not the others.

## 🧠 Self-check

**Q1. In BM25, what do idf, k1 and b each control?**
A: idf rewards rare, informative words over common ones; k1 sets how quickly extra repetitions of a word stop adding score (saturation); b sets how strongly long chunks are penalised for being long (0 = no penalty, 1 = full).

**Q2. Give two reasons the production RAG course builds keyword search before vector search.**
A: Keywords excel at exact technical terms, IDs and precise phrases; results are interpretable (you can see why something matched); and it's fast with no embedding model needed.

**Q3. What's the core trade-off in choosing chunk size, and what does overlap buy you?**
A: Large chunks lose retrieval precision (one chunk covers many topics), small chunks lose context (the idea is split). Overlap repeats text across chunk boundaries so an answer straddling a boundary isn't lost.

**Q4. Your question “How do agents forget earlier rules?” gets poor hits, but the pack covers compaction well. What's the likely failure and what are two fixes?**
A: A wording mismatch: BM25 only matches exact words, so “forget” doesn't hit “compaction”. Fixes: rewrite the query with the field's vocabulary, add embedding-based search (m21), or retrieve more and rerank.

**Q5. How does BM25 differ from a forager applying the marginal value theorem?**
A: A forager learns patch quality from experience; BM25 never learns and always gives the same ranking. It's blind to synonyms, and it doesn't account for diminishing returns from redundant chunks the agent has already read.
