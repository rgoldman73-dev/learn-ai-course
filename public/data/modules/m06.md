## 🌿 The ecology hook

“Do warmer streams have fewer stoneflies?” is a hypothesis, not a protocol. Before anyone goes into the field you specify the sites, the sampling method, the response variable, the replication, and what result would count as an answer. A field team handed only the hypothesis will come back with *something*, and it probably won't be what you needed.

A prompt to a coding agent is a protocol handed to a very fast, very willing field team that never asks for clarification unless you tell it to. In m02 you saw that a precise question gives a sharply peaked answer distribution and a vague one gives a flat one. Today you'll turn that into habits.

## 📖 Concept: writing a protocol, not a wish

### Start with questions, not edits

Boris, who created Claude Code, recommends **codebase Q&A** as the first thing anyone does with it. Before editing anything, ask questions: how is this function used, why does this function have so many arguments (look through the git history), what did I ship this week. He says this is how Anthropic onboards new technical hires, and that it cut onboarding from two or three weeks to two or three days [S:2106712905001365608]. Q&A is safe (nothing changes), and it teaches you where the agent's abilities end before you trust it with edits [S:2106712905001365608].

### Anatomy of a good prompt

The Claude Code guide gives a compact recipe: **a goal, a scope and a done criterion** [S:2104402058963026288]. Its example: the signup form fails with uppercase emails; reproduce it with a test, fix it in the validation layer, and don't stop until all tests pass.

| Part | Weak | Strong |
|---|---|---|
| Goal | “make my analysis better” | “make `diversity.py` report Shannon H′ per site” |
| Scope | (none) | “only edit `diversity.py`; don't touch `data/`” |
| Done criterion | (none) | “done when `python3 -m unittest` passes and the output matches `expected.csv`” |

Boris adds two multipliers [S:2106712905001365608]:

- **Plan before code.** Ask it to brainstorm or make a plan and get your approval before writing code. No special mode is needed. Saying “before you write code, make a plan” is enough.
- **Give it a way to check its work**: unit tests, screenshots, a script that must pass. With feedback it iterates, and two or three iterations often get it close to right.

The guide orders the whole cycle as **explore, plan, execute, verify**, and points out that fixing a plan takes seconds while fixing bad code takes minutes [S:2104402058963026288]. Its sharpest warning: Claude will always give you an answer, but that doesn't mean the answer is correct, so read every diff [S:2104402058963026288].

### Habits that save context and rework

Ruben Hassid's rules come at the same goal from the usage side [S:2107712638381941071]:

- **“Ask me questions first.”** Instead of a 500-word prompt that gets re-read every turn, write one line of intent plus success criteria and ask Claude to interview you with multiple-choice questions before it starts.
- **Put all your asks in one message.** Each extra message is another full re-read.
- **Speak, don't type.** Spoken prompts tend to carry more context. Boris uses dictation for the same reason [S:2106712905001365608].
- **Plan in text; ask for the file last.** Agree the outline before generating the long artifact.
- **When a chat goes sideways, start over** with a short brief instead of piling corrections on top. Every “No, I meant…” stays in the context.

### Ask for output you can check

From m03: you can also specify the *form* of the answer. Karpathy suggests asking for controlled language (ASD-STE100), diagrams or an HTML page, because those are easier to understand and check [S:2105819303471976479]. “Summarise the result in five short ASD-STE100 sentences, one claim each” is part of a good protocol.

### A protocol template

```text
Goal:     <one sentence: what should exist or be true at the end>
Context:  <files or docs to read first; the map in AGENTS.md>
Scope:    <what you may change; what you must not touch>
Done:     <a command or check that proves it, e.g. tests pass, output matches>
Process:  Ask me up to 3 questions first. Then show a plan and wait for my OK.
Report:   <format: e.g. 5 ASD-STE100 sentences + the diff>
```

You won't need every line every time. The **Done** line matters most, because it's what turns “looks right” into “is right”.

> **Where the metaphor fails.** A field protocol is read by people who share your training. A good assistant notices the gap and asks before collecting a single sample, and a reviewer often catches the problem before the season starts. A coding agent fills every gap with a confident guess and starts at once. Nobody reviews the protocol before the run unless you build that step in (“ask me questions first”, “show me a plan”). And the run is cheap enough that you're tempted to skip design altogether, which is exactly when it goes wrong.

## 🧠 Self-check

**Q1. What three parts does the Claude Code guide say a good prompt needs?**
A: A goal, a scope and a done criterion. For example: reproduce the bug with a test (goal), fix it in the validation layer only (scope), and don't stop until all tests pass (done).

**Q2. Why does Boris recommend codebase Q&A as the first use of a coding agent?**
A: It's safe, because nothing is edited, and it teaches you how to prompt and where the agent's abilities end before you trust it with changes. It's also directly useful: at Anthropic it shortened technical onboarding from weeks to days.

**Q3. Why is “ask me questions before you start” cheaper than writing a very long prompt?**
A: A long prompt is re-read on every turn of the session, while a short intent plus a few multiple-choice answers carries the same information in fewer tokens. It also surfaces the gaps you didn't know you'd left.

**Q4. The agent says “Done, everything works.” What should your prompt have included to make that claim checkable?**
A: A done criterion that a command can verify, such as a test suite that passes or output that matches a reference file, plus a request to run it and show the result. Without that, “done” is just the agent's opinion.

**Q5. How does the field-protocol analogy break?**
A: A field team or reviewer usually questions a vague protocol before data collection starts. An agent fills gaps with confident guesses and starts immediately, so you have to build the questioning and planning steps into the prompt or the instruction file yourself.
